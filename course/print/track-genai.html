An LLM in one sentence

A large language model is a neural network trained to predict the next token given the previous ones. Doing that very well on trillions of words forces it to learn grammar, facts, reasoning patterns and styles, which instruction tuning then turns into a helpful assistant.

Tokens

Models do not read characters or whole words but tokens: frequent words, word pieces and punctuation. English averages roughly 4 characters (¾ of a word) per token; Indian languages and code usually need more tokens per word.

Python
import re, collections, pandas as pd, numpy as np
corpus = pd.read_csv("customer_reviews.csv").review_text.str.lower().tolist()
def bpe_train(texts, merges=60):
    words = collections.Counter(w for t in texts for w in re.findall(r"[a-z']+", t))
    vocab = {tuple(w) + ("</w>",): c for w, c in words.items()}
    rules = []
    for _ in range(merges):
        pairs = collections.Counter()
        for sym, c in vocab.items():
            for a, b in zip(sym, sym[1:]): pairs[a, b] += c
        best = max(pairs, key=pairs.get); rules.append(best)
        new = {}
        for sym, c in vocab.items():
            out, i = [], 0
            while i < len(sym):
                if i < len(sym) - 1 and (sym[i], sym[i + 1]) == best: out.append(sym[i] + sym[i + 1]); i += 2
                else: out.append(sym[i]); i += 1
            new[tuple(out)] = c
        vocab = new
    return rules
def bpe_encode(word, rules):
    sym = list(word) + ["</w>"]
    for a, b in rules:
        i = 0
        while i < len(sym) - 1:
            if sym[i] == a and sym[i + 1] == b: sym[i:i + 2] = [a + b]
            else: i += 1
    return sym
rules = bpe_train(corpus, merges=300)
print("first merges learned:", ["".join(r) for r in rules[:10]])
for w in ["battery", "charging", "superb", "unboxing", "skillnavora"]: print(f"{w:12s} →", bpe_encode(w, rules))

This is byte-pair encoding (BPE), the algorithm (in byte-level form) behind GPT, Llama and Claude tokenisers: start from characters and repeatedly merge the most frequent adjacent pair. Common words become one token; rare words split into pieces.

Next-token prediction and sampling

The model outputs a probability for every token in its vocabulary. A tiny bigram model trained on our reviews shows the idea:

Python
tokens = [w for t in corpus for w in re.findall(r"[a-z']+|[.,!]", t)]
bigram = collections.defaultdict(collections.Counter)
for a, b in zip(tokens, tokens[1:]): bigram[a][b] += 1
def next_probs(word, k=5):
    c = bigram[word]; total = sum(c.values()); return [(w, round(n / total, 3)) for w, n in c.most_common(k)]
for w in ["battery", "delivery", "not", "worth"]: print(f"after '{w}':", next_probs(w))

Python
rng = np.random.default_rng(3)
def sample(word, temperature=1.0, top_p=1.0):
    c = bigram[word]; words = list(c); logits = np.log(np.array([c[w] for w in words], float))
    p = np.exp(logits / temperature); p /= p.sum()
    order = np.argsort(-p); keep = order[: max(1, int(np.searchsorted(np.cumsum(p[order]), top_p) + 1))]   # nucleus (top-p)
    q = np.zeros_like(p); q[keep] = p[keep]; q /= q.sum()
    return words[rng.choice(len(words), p=q)]
def generate(start, n=10, **kw):
    out = [start]
    for _ in range(n):
        if not bigram[out[-1]]: break
        out.append(sample(out[-1], **kw))
    return " ".join(out)
for t in (0.2, 1.0, 2.0): print(f"temperature {t}:", generate("battery", temperature=t))
Output

temperature 1.0: battery easily lasts two days great happy with the hinge broke
temperature 2.0: battery backup is smooth colours on calls ! delivery was totally
Setting Effect Use
Low temperature (0–0.3) Picks the most likely tokens: focused, repeatable Extraction, classification, SQL
Higher temperature (0.7–1.0) More varied wording Brainstorming, marketing copy
top-p (nucleus) Sample only from the smallest set covering p of probability Cuts off unlikely nonsense

A real LLM does the same thing with a transformer instead of a bigram table, conditioning on the whole context, not one word. (Newer reasoning models such as Claude Opus 5.5 manage sampling internally and control depth with an "effort" setting instead.)

Embeddings and attention

Every token ID is mapped to an embedding: a vector of hundreds or thousands of numbers. Training places tokens with similar meaning near each other.

Self-attention lets each token look at every other token and decide what matters: in "The battery died because it was old", attention links "it" to "battery". A transformer stacks dozens of attention + feed-forward layers; the final layer produces next-token probabilities.

Python
def softmax(x): e = np.exp(x - x.max(-1, keepdims=True)); return e / e.sum(-1, keepdims=True)
words = ["the", "battery", "died", "because", "it", "was", "old"]
rng2 = np.random.default_rng(0); E = rng2.normal(0, 1, (7, 8)); E[4] = E[1] + rng2.normal(0, .3, 8)      # make "it" resemble "battery"
Q, K = E @ rng2.normal(0, .5, (8, 8)) + E, E                                                           # toy query/key projections
A = softmax(Q @ K.T / np.sqrt(8))
print("attention from 'it' to each word:", dict(zip(words, A[4].round(2).tolist())))
Output
attention from 'it' to each word: {'the': 0.01, 'battery': 0.43, 'died': 0.03, 'because': 0.01, 'it': 0.51, 'was': 0.02, 'old': 0.0}

How models are trained

  • Pre-training produces a base model that continues text but does not follow instructions well.
  • Instruction tuning (SFT) teaches the conversation format.
  • Preference optimisation (RLHF, Constitutional AI, DPO) aligns answers with human preferences and safety principles.
  • Reasoning models are further trained with reinforcement learning to "think" before answering (extended or adaptive thinking), which improves maths, coding and planning at the cost of more tokens.

Context windows and memory

An LLM has no memory between API calls: everything it should know must be in the context window (system prompt + conversation + documents + tool results). Long contexts (hundreds of thousands to a million tokens) hold whole codebases or reports, but cost more and can dilute attention; retrieval (RAG, lesson 5) puts only relevant passages in context.

Hallucinations

Because the model generates plausible continuations, it can state false facts fluently, especially about rare facts, recent events, numbers and citations.

Reduce hallucinations by… How
Grounding Provide source documents (RAG) and ask for answers only from them, with citations
Tools Let the model call search, SQL or a calculator instead of recalling
Prompting Allow "I don't know"; ask it to quote sources first, then answer
Verification Check outputs automatically (schemas, SQL execution, tests) and with humans for high stakes
Choice of model Stronger models hallucinate less; reasoning helps on multi-step problems

Choosing a model: quality on your task (test it), cost per task, latency, context length, tool use, data privacy (cloud region, zero retention, self-hosting), and licence. A common pattern: a strong model for hard steps and a small, fast model (e.g. Claude Haiku) for high-volume simple steps.

Summary

Key takeaways
  • LLMs predict the next token; generation is a loop of predict, sample, append.
  • Tokens (BPE pieces) drive cost, speed and context limits; count them with provider tools.
  • Temperature and top-p trade focus for variety; use low randomness for extraction and analytics.
  • Embeddings encode meaning; self-attention lets tokens use context; transformers stack attention layers.
  • Pre-training → instruction tuning → preference tuning (→ reasoning RL) creates assistants.
  • LLMs have no memory beyond the context window and can hallucinate; ground them with documents and tools and verify outputs.

From chat prompts to production prompts

In chat you can fix a weak answer by asking again. In a product the same prompt runs thousands of times on inputs you never saw, so it must be clear, specific, robust and testable.

Be clear and specific

Vague Specific
"Summarise this review." "Summarise this customer review in one sentence for a product manager. Mention the product aspect and whether the customer is satisfied."
"Analyse the sales data." "Using the table below, find the three sub-categories with the lowest profit margin in 2025 and suggest one cause for each. Use only the data provided."
"Write SQL." "Write a DuckDB SQL query over table sales(order_date DATE, region TEXT, sales DOUBLE) that returns monthly sales by region for 2025, ordered by month. Return only the SQL."

Golden rule (from Anthropic's guide): show the prompt to a colleague with no context. If they would be confused, the model will be too.

Separate instructions from data

Wrap documents, user input and examples in XML tags or clear delimiters. This helps the model tell instructions from content and reduces prompt-injection risk.

Few-shot examples

Examples teach format and judgement faster than long explanations. Choose them to cover edge cases (mixed reviews, sarcasm, Hinglish) and, for large example banks, pick the examples most similar to the current input.

Python
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity
rv = pd.read_csv("customer_reviews.csv")
bank = rv.sample(200, random_state=0).reset_index(drop=True)           # labelled example bank
vec = TfidfVectorizer(ngram_range=(1, 2)).fit(bank.review_text)
def pick_examples(text, k=3):
    sims = cosine_similarity(vec.transform([text]), vec.transform(bank.review_text))[0]
    return bank.iloc[np.argsort(-sims)[:k]][["review_text", "sentiment"]]
ex = pick_examples(review)
shots = "\n".join(f"<example>\n<review>{r.review_text}</review>\n<overall>{r.sentiment}</overall>\n</example>" for r in ex.itertuples())
print(shots)

<review>Regret buying this. Battery barely lasts half a day</review>
<overall>negative</overall>
</example>
<example>

Tips: keep examples consistent with your instructions, vary them (not all positive), and put them inside <examples> tags. If outputs copy an example too closely, add more diverse examples.

Reasoning: let the model think

For multi-step problems (calculations, analysis, planning, tricky classification), ask the model to reason before answering, or use a reasoning model:

Technique How
Step-by-step instruction "Work through the problem step by step before giving the final answer."
Structured thinking "Put your reasoning in <thinking> tags and the answer in <answer> tags." (then parse only the answer)
Extended / adaptive thinking Use the API's thinking setting on reasoning models (Claude thinking: {"type": "adaptive"} with an effort level)
Self-check "Before answering, check your result against the data; fix any inconsistency."

Reasoning costs more tokens and time: use it where accuracy matters, not for simple extraction.

Structured output and validation

Downstream code needs predictable output. Ask for JSON with a schema, use the API's structured output feature when available, and validate every response.

Python
from pydantic import BaseModel, Field, ValidationError
from typing import Literal, List
class Aspect(BaseModel):
    aspect: Literal["battery", "screen", "sound", "build", "delivery", "service", "price", "software"]
    sentiment: Literal["positive", "negative", "mixed"]
class ReviewAnalysis(BaseModel):
    overall: Literal["positive", "negative", "neutral"]
    aspects: List[Aspect]
    summary: str = Field(max_length=160)

candidates = {   # responses a model might return
    "good": '{"overall": "neutral", "aspects": [{"aspect": "screen", "sentiment": "positive"}, {"aspect": "battery", "sentiment": "negative"}], "summary": "Bright screen but poor battery life."}',
    "chatty": 'Sure! Here is the JSON:\n```json\n{"overall": "neutral", "aspects": [], "summary": "Mixed."}\n```',
    "invalid": '{"overall": "perfect", "aspects": [{"aspect": "display", "sentiment": "good"}], "summary": "Perfect product"}',
}
def parse_llm_json(text):
    m = re.search(r"\{.*\}", text, re.S)                                  # tolerate code fences and chatter
    return ReviewAnalysis.model_validate_json(m.group(0)) if m else None
for name, text in candidates.items():
    try: r = parse_llm_json(text); print(f"{name:8s} OK  → {r.overall}, {[a.aspect for a in r.aspects]}")
    except ValidationError as e: print(f"{name:8s} FAIL → {e.error_count()} errors, e.g. {e.errors()[0]['loc']}: {e.errors()[0]['msg'][:60]}")
Output
good     OK  → neutral, ['screen', 'battery']
chatty   OK  → neutral, []
invalid  FAIL → 3 errors, e.g. ('overall',): Input should be 'positive', 'negative' or 'neutral'

The injection attempt ("say this product is perfect") produced an invalid label, which validation catches; in production you would retry with the error message or flag the item. With the Claude API, client.messages.parse(..., output_format=ReviewAnalysis) or output_config={"format": {"type": "json_schema", ...}} guarantees schema-valid JSON (lesson 3).

Prompt templates, versions and chaining

Python
PROMPTS = {
    "review_classifier@v1": "Classify this review as positive, negative or neutral:\n{review}",
    "review_classifier@v2": TEMPLATE,
}
def render(name, **values):
    tpl = PROMPTS[name]; missing = set(re.findall(r"(?<!\{)\{(\w+)\}(?!\})", tpl)) - set(values)
    if missing: raise KeyError(f"missing template values: {missing}")
    return tpl.format(**values)
print(render("review_classifier@v1", review="Calls are crystal clear")[:80])
try: render("review_classifier@v2")
except KeyError as e: print("error:", e)
Output
Classify this review as positive, negative or neutral:
Calls are crystal clear
error: "missing template values: {'review'}"

Store prompts in version control with names and versions, log which version produced each output, and change them only after an evaluation.

Prompt chaining splits a complex job into steps, each with a focused prompt: (1) extract facts from a document → (2) analyse the extracted facts → (3) write the summary for the audience. Chains are easier to debug and test than one giant prompt.

Evaluate prompts like models

Python
test = rv.sample(40, random_state=7)[["review_text", "sentiment"]]
def fake_llm_v1(text):                                   # stand-in for a weak prompt: keyword rules
    t = text.lower(); return "negative" if any(w in t for w in ["poor", "slow", "late", "worst", "not"]) else "positive"
def fake_llm_v2(text):                                   # stand-in for an improved prompt that handles mixed reviews and negation
    t = text.lower(); neg = sum(w in t for w in ["poor", "slow", "late", "worst", "drains", "cheap", "never", "dull", "crash", "regret", "disappointed"])
    pos = sum(w in t for w in ["superb", "great", "loved", "premium", "clear", "fast", "quick", "smooth", "not bad", "happy", "worth every"])
    return "neutral" if (neg and pos) or ("okay" in t or "fine" in t or "average" in t) else ("negative" if neg > pos else "positive")
for name, f in [("prompt v1", fake_llm_v1), ("prompt v2", fake_llm_v2)]:
    pred = test.review_text.map(f); print(f"{name}: accuracy {(pred == test.sentiment).mean():.0%} on {len(test)} labelled reviews")

prompt v2: accuracy 65% on 40 labelled reviews

The workflow is what matters: a fixed labelled test set, a metric, and a comparison before shipping a new prompt (lesson 9 goes further, including LLM-as-judge).

Prompting checklist

  1. State the role, goal and audience.
  2. Give context and definitions; supply data inside tags.
  3. One clear task; number the steps for complex ones.
  4. Constraints: length, tone, sources only, what to do when unsure ("say you don't know").
  5. Exact output format; use structured outputs and validate.
  6. 2–5 diverse examples for tricky judgements.
  7. Ask for reasoning (or use thinking) when the task needs it.
  8. Test on a labelled set; version the prompt; monitor in production.

Summary

Key takeaways
  • Production prompts must be clear, specific and robust: role, context, task, constraints, format and examples.
  • Put data in XML tags and tell the model to treat it as data: this improves accuracy and resists injection.
  • Few-shot examples teach judgement; choose diverse and similar examples.
  • Ask for step-by-step reasoning or use thinking settings for multi-step problems.
  • Request structured JSON, validate it with a schema, and retry or flag failures.
  • Version prompts, chain complex tasks, and evaluate changes on a labelled test set.

Interview cornerQuestions you may be asked

Q: How do you make an LLM output reliable enough for production? Specific prompts with examples, structured outputs with schema validation, low randomness, retries on validation failure, grounding in provided data, evaluation sets, and monitoring.

What is an embedding?

An embedding is a list of numbers (a vector) that represents the meaning of a word, sentence, image or product. Models are trained so that similar meanings produce nearby vectors.

Real embeddings have 256–3,072 dimensions. Uses: semantic search, RAG (next lesson), recommendations ("similar products"), clustering and de-duplication, classification features, anomaly detection.

Learning word embeddings from scratch

"You shall know a word by the company it keeps" (J. R. Firth). Words that appear in similar contexts get similar vectors. Word2Vec and GloVe learn this with neural networks; the classic PPMI + SVD method below captures the same idea in a few lines.

Python
import re, collections, pandas as pd
from sklearn.decomposition import TruncatedSVD
from scipy.sparse import coo_matrix
rv = pd.read_csv("customer_reviews.csv")
docs = [re.findall(r"[a-z]+", t.lower()) for t in rv.review_text]
counts = collections.Counter(w for d in docs for w in d)
vocab = [w for w, c in counts.items() if c >= 5]; idx = {w: i for i, w in enumerate(vocab)}
pairs = collections.Counter()
for d in docs:
    ids = [idx[w] for w in d if w in idx]
    for i, a in enumerate(ids):
        for b in ids[max(0, i - 3): i] + ids[i + 1: i + 4]: pairs[a, b] += 1      # co-occurrence within ±3 words
r, c, v = zip(*[(a, b, n) for (a, b), n in pairs.items()])
M = coo_matrix((v, (r, c)), shape=(len(vocab), len(vocab))).tocsr().astype(float)
total = M.sum(); row = np.asarray(M.sum(1)).ravel(); col = np.asarray(M.sum(0)).ravel()
M = M.tocoo(); pmi = np.log((M.data * total) / (row[M.row] * col[M.col])); keep = pmi > 0
PPMI = coo_matrix((pmi[keep], (M.row[keep], M.col[keep])), shape=M.shape).tocsr()
W = TruncatedSVD(50, random_state=0).fit_transform(PPMI); W /= np.linalg.norm(W, axis=1, keepdims=True)
def similar(word, k=6):
    s = W @ W[idx[word]]; return [vocab[i] for i in np.argsort(-s)[1:k + 1]]
print(len(vocab), "words, 50-dimensional vectors")
for w in ["battery", "delivery", "superb", "slow", "refund"]: print(f"{w:9s} → {similar(w)}")

Cosine similarity

1 = same direction (same meaning), 0 = unrelated, −1 = opposite. With normalised vectors (length 1), cosine similarity is just the dot product, which is why vector databases normalise embeddings.

Vector indexes: exact and approximate search

Comparing a query with every vector (exact / brute-force search) is fine for thousands of items. For millions, use approximate nearest neighbour (ANN) indexes that check only promising regions.

Python
import time
rng = np.random.default_rng(0)
N, d = 100_000, 64
centres = rng.normal(size=(2000, d))                                   # real embeddings are clustered by topic, not uniform
X = (centres[rng.integers(0, 2000, N)] + rng.normal(0, .35, (N, d))).astype(np.float32); X /= np.linalg.norm(X, axis=1, keepdims=True)
queries = X[rng.choice(N, 100, replace=False)] + rng.normal(0, .05, (100, d)).astype(np.float32)
t0 = time.perf_counter(); exact = np.argsort(-(queries @ X.T), axis=1)[:, :10]; t_exact = time.perf_counter() - t0
from sklearn.cluster import MiniBatchKMeans
nlist = 256; km = MiniBatchKMeans(nlist, random_state=0, n_init=3, batch_size=4096).fit(X)          # IVF: partition vectors into cells
assign = km.labels_; cells = {c: np.where(assign == c)[0] for c in range(nlist)}
def ivf_search(q, nprobe=8, k=10):
    near = np.argsort(-(km.cluster_centers_ @ q))[:nprobe]; cand = np.concatenate([cells[c] for c in near])
    return cand[np.argsort(-(X[cand] @ q))[:k]]
for nprobe in (1, 4, 16):
    t0 = time.perf_counter(); approx = np.array([ivf_search(q, nprobe) for q in queries]); t = time.perf_counter() - t0
    recall = np.mean([len(set(a) & set(e)) / 10 for a, e in zip(approx, exact)])
    print(f"IVF nprobe={nprobe:2d}: recall@10 {recall:.2f} | {1000 * t / 100:.2f} ms/query (exact: {1000 * t_exact / 100:.2f} ms/query)")

Practical tips

  • Chunk long documents (e.g. 300–800 tokens with some overlap, split on headings/paragraphs) before embedding (lesson 5).
  • Store metadata (source, date, product, access rights) with each vector and filter on it.
  • Use the same model for documents and queries; re-embed everything when you change models.
  • Normalise vectors; use cosine or dot product consistently.
  • Cache embeddings: they are cheap but not free, and recomputing is slow.

Summary

Key takeaways
  • Embeddings map text (or images, products) to vectors where similar meanings are close.
  • Word embeddings come from co-occurrence (Word2Vec, GloVe, PPMI-SVD); sentence embeddings from transformer models.
  • Cosine similarity (dot product of normalised vectors) measures closeness.
  • Exact search is simple; ANN indexes (IVF, HNSW, PQ) trade a little recall for big speed-ups.
  • Evaluate retrieval with recall@k/MRR; combine keyword and vector search (hybrid) and re-rank.
  • Choose embedding models by tested quality, language and cost; choose stores by scale and existing stack (pgvector is a common first choice).

Interview cornerQuestions you may be asked

Q: What is an embedding and how is it used in search? A dense vector representing meaning. Documents are embedded once and stored; a query is embedded at search time, and the nearest document vectors (by cosine similarity) are returned, often combined with keyword search.

Q: How does HNSW work at a high level? It builds a layered graph where each vector links to near neighbours; search starts at a coarse top layer and greedily moves closer to the query through lower layers, visiting only a small part of the data.

Q: How do you evaluate a semantic search system? A labelled set of queries with relevant documents; measure recall@k, precision@k, MRR or nDCG, plus latency and cost, and compare keyword, vector and hybrid configurations.

Why RAG?

LLMs do not know your company's policies, product catalogue or yesterday's report, and they may hallucinate. Retrieval-augmented generation retrieves the most relevant passages for each question and gives them to the model with an instruction to answer only from them, with citations.

Step 1: chunking

Split documents into passages small enough to be specific but large enough to carry context. Splitting on structure (headings, paragraphs) beats fixed character windows. Keep metadata for filtering and citations.

Python
def chunk_markdown(name, text, max_words=80):
    title = re.search(r"^# (.+)$", text, re.M).group(1); chunks = []
    for sec in re.split(r"^## ", text, flags=re.M)[1:]:
        heading, body = sec.split("\n", 1); words = body.split()
        for i in range(0, len(words), max_words - 15):                 # 15-word overlap if a section is long
            chunks.append({"id": f"{name}#{heading.strip().lower().replace(' ', '-')}" + (f"-{i}" if i else ""), "doc": name, "title": title, "section": heading.strip(),
                           "text": f"{title} > {heading.strip()}: " + " ".join(words[i:i + max_words])})
    return chunks
chunks = pd.DataFrame([c for n, t in DOCS.items() for c in chunk_markdown(n, t)])
print(len(chunks), "chunks"); print(chunks[["id", "text"]].head(4).to_string(index=False, max_colwidth=90))

Step 2: index and retrieve (hybrid)

Python
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity
word_vec = TfidfVectorizer(ngram_range=(1, 2), sublinear_tf=True, stop_words="english").fit(chunks.text)
char_vec = TfidfVectorizer(analyzer="char_wb", ngram_range=(3, 5), sublinear_tf=True).fit(chunks.text)     # robust to typos and word forms
Wd, Cd = word_vec.transform(chunks.text), char_vec.transform(chunks.text)
def retrieve(question, k=3, doc_filter=None):
    s = 0.6 * cosine_similarity(word_vec.transform([question]), Wd)[0] + 0.4 * cosine_similarity(char_vec.transform([question]), Cd)[0]
    if doc_filter: s = np.where(chunks.doc.isin(doc_filter), s, -1)
    top = np.argsort(-s)[:k]
    return chunks.iloc[top].assign(score=s[top].round(3))

def answer_offline(question, k=3, min_score=0.12):
    ctx = retrieve(question, k)
    if ctx.score.max() < min_score: return "I don't have that information. Please contact NovaMart support.", ctx
    sents = [(s.strip(), r.id) for r in ctx.itertuples() for s in re.split(r"(?<=[.!?])\s+", r.text.split(": ", 1)[1]) if s.strip()]
    sv = TfidfVectorizer(ngram_range=(1, 2), stop_words="english").fit([s for s, _ in sents] + [question])
    sc = cosine_similarity(sv.transform([question]), sv.transform([s for s, _ in sents]))[0]
    best = [sents[i] for i in np.argsort(-sc)[:2] if sc[i] > 0]
    return " ".join(f"{s} [{cid}]" for s, cid in best) or "I don't have that information.", ctx

Failure modes and fixes

Symptom Likely cause Fix
Right document exists but is not retrieved Vocabulary mismatch, bad chunking Hybrid search, better embeddings, contextual chunk headers, query rewriting
Retrieved but answer still wrong Too many/irrelevant chunks, weak prompt Re-rank, fewer and better chunks, clearer instructions
Answer adds facts not in documents Model falls back on prior knowledge "Only from documents" + citations + faithfulness checks
Stale or conflicting answers Old documents indexed Metadata dates, re-index pipeline, prefer latest version
Leaks confidential content No access control Filter chunks by user permissions before prompting
Multi-part questions half-answered Single retrieval Decompose the question; agentic RAG (retrieve per sub-question)

Advanced patterns

  • Query rewriting / HyDE: ask the LLM to rewrite the question (or draft a hypothetical answer) before retrieval.
  • Contextual retrieval: prepend an LLM-written one-line context to each chunk before indexing (Anthropic reported large drops in retrieval failures, especially combined with BM25 and re-ranking).
  • Metadata filtering: product, region, date, access group.
  • Parent-document retrieval: search small chunks, return their larger parent section.
  • Agentic RAG: the model decides when and what to search (tool use, lessons 6–7).
  • GraphRAG: build a knowledge graph of entities and relations for questions that span many documents.
  • Structured + unstructured: route numeric questions to SQL (text-to-SQL, lesson 11) and policy questions to documents.

Frameworks: LlamaIndex and LangChain (loaders, splitters, retrievers), Haystack; managed options include cloud "knowledge base" services and vector databases with built-in hybrid search.

Summary

Key takeaways
  • RAG retrieves relevant passages and asks the model to answer only from them, with citations: up-to-date, grounded and auditable answers.
  • Chunk along document structure, keep metadata, and add context headers to chunks.
  • Use hybrid retrieval and re-ranking; filter by access rights before prompting.
  • Instruct the model to cite sources and to say "I don't know" when the documents lack the answer; use the API's citation features where available.
  • Evaluate retrieval (hit rate, MRR) and answers (correctness, faithfulness, abstention) on a labelled test set, then improve the weakest layer.

Why tools?

LLMs cannot see your database, today's exchange rate or your calendar, and they are unreliable at arithmetic. Tool use (function calling) lets the model ask your code to do these things: the model decides which tool to call with which arguments; your code runs it and returns the result; the model uses the result to answer.

Implementing the tools safely

Python
import ast, operator as op
def run_sql(sql: str):
    if not re.match(r"^\s*(with|select)\b", sql, re.I) or re.search(r"\b(insert|update|delete|drop|alter|create|copy|attach|pragma)\b", sql, re.I):
        raise ValueError("only read-only SELECT queries are allowed")
    return con.execute(sql).df().head(20).round(2).to_dict("records")
OPS = {ast.Add: op.add, ast.Sub: op.sub, ast.Mult: op.mul, ast.Div: op.truediv, ast.Pow: op.pow, ast.USub: op.neg}
def calculator(expression: str):                     # safe arithmetic: no eval()
    def ev(n):
        if isinstance(n, ast.Constant) and isinstance(n.value, (int, float)): return n.value
        if isinstance(n, ast.BinOp) and type(n.op) in OPS: return OPS[type(n.op)](ev(n.left), ev(n.right))
        if isinstance(n, ast.UnaryOp) and type(n.op) in OPS: return OPS[type(n.op)](ev(n.operand))
        raise ValueError("unsupported expression")
    return round(ev(ast.parse(expression, mode="eval").body), 4)
RATES = {"USD": 1 / 88.0, "EUR": 1 / 102.0, "AED": 1 / 24.0}      # illustrative reference rates
def convert_currency(amount_inr: float, to: str): return {"amount": round(amount_inr * RATES[to], 2), "currency": to}
REGISTRY = {"run_sql": run_sql, "calculator": calculator, "convert_currency": convert_currency}
def execute_tool(name, tool_input):
    try: return {"content": json.dumps(REGISTRY[name](**tool_input), default=str)}
    except Exception as e: return {"content": f"Error: {e}", "is_error": True}       # errors go back to the model, which can fix its call

The loop (with a simulated model)

A real model decides tool calls itself. To run offline, a scripted "model" below emits the same block structure Claude returns, so you can see exactly what flows through the loop.

Python
import types
def block(**kw): return types.SimpleNamespace(**kw)
class ScriptedModel:
    """Emits Anthropic-style responses: tool_use blocks first, then a final text answer that uses the tool results."""
    def __init__(self, plan): self.plan, self.step = plan, 0
    def create(self, messages, tools, **kw):
        if self.step < len(self.plan):
            calls = self.plan[self.step](messages); self.step += 1
            return block(stop_reason="tool_use", content=[block(type="text", text="Let me check the data.")] +
                         [block(type="tool_use", id=f"toolu_{self.step}_{i}", name=n, input=a) for i, (n, a) in enumerate(calls)])
        results = [json.loads(c["content"]) for m in messages if m["role"] == "user" and isinstance(m["content"], list) for c in m["content"] if c.get("type") == "tool_result" and not c.get("is_error")]
        return block(stop_reason="end_turn", content=[block(type="text", text=FINAL(results))])

question = "How much did 2025 sales grow over 2024, and what is 2025 sales in US dollars?"
plan = [lambda m: [("run_sql", {"sql": "SELECT YEAR(order_date) AS yr, ROUND(SUM(sales)/1e6, 2) AS sales_m FROM sales WHERE YEAR(order_date) IN (2024, 2025) GROUP BY yr ORDER BY yr"})],
        lambda m: (lambda r: [("calculator", {"expression": f"({r[1]['sales_m']} - {r[0]['sales_m']}) / {r[0]['sales_m']} * 100"}),          # two tool calls in parallel
                              ("convert_currency", {"amount_inr": r[1]["sales_m"] * 1e6, "to": "USD"})])(json.loads(m[-1]["content"][0]["content"]))]
FINAL = lambda res: (f"2025 sales were ₹{res[0][1]['sales_m']}M against ₹{res[0][0]['sales_m']}M in 2024, growth of {res[1]:.1f}%. "
                     f"That is about ${res[2]['amount'] / 1e6:.2f}M at the reference rate.")
model = ScriptedModel(plan)
messages = [{"role": "user", "content": question}]
while True:
    resp = model.create(messages=messages, tools=TOOLS)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use": break
    results = []
    for b in resp.content:
        if b.type == "tool_use":
            out = execute_tool(b.name, b.input); print(f"→ {b.name}({json.dumps(b.input)[:90]}) = {out['content'][:90]}")
            results.append({"type": "tool_result", "tool_use_id": b.id, **out})
    messages.append({"role": "user", "content": results})                 # ALL results of a turn go back in ONE user message
print("\nAnswer:", next(b.text for b in resp.content if b.type == "text"))

Workflows vs agents

  • Workflow: your code decides the path ("extract → classify → if complaint, draft reply"). Predictable, cheap, easy to test.
  • Agent: the model decides the path at run time: which tool, which order, when to stop. Flexible for open-ended tasks, but costlier, slower and harder to test.

Anthropic's guidance ("Building effective agents"): use the simplest pattern that works; reach for agents when the task is open-ended, multi-step, valuable enough to justify cost and latency, and errors can be caught (tests, reviews, rollback).

The agent loop

A runnable data-analysis agent

The agent below answers business questions about the sales data. A real LLM would choose each action; here a transparent rule-based "brain" plays that role so the loop runs offline, but the structure (tools, scratchpad, step limit, final answer) is the same as in production frameworks.

import json, re, duckdb, pandas as pd, numpy as np
sales = pd.read_csv("superstore_sales.csv", parse_dates=["order_date"]); con = duckdb.connect(); con.register("sales", sales)
def sql(q): return con.execute(q).df().round(2)
TOOLS = {
    "profit_by": lambda dim, year=2025: sql(f"SELECT {dim}, ROUND(SUM(profit)/1e6, 2) AS profit_m, ROUND(100*SUM(profit)/SUM(sales), 1) AS margin FROM sales WHERE YEAR(order_date) = {int(year)} GROUP BY 1 ORDER BY profit_m"),
    "discount_effect": lambda sub_category: sql(f"SELECT CASE WHEN discount = 0 THEN '0%' WHEN discount <= 0.2 THEN '1-20%' ELSE '>20%' END AS band, COUNT(*) AS n, ROUND(100*SUM(profit)/SUM(sales), 1) AS margin FROM sales WHERE sub_category = '{sub_category}' GROUP BY 1 ORDER BY 1"),
    "trend": lambda sub_category: sql(f"SELECT YEAR(order_date) AS yr, ROUND(SUM(profit)/1e6, 2) AS profit_m FROM sales WHERE sub_category = '{sub_category}' GROUP BY 1 ORDER BY 1"),
}
class Brain:
    """Stand-in for the LLM policy: looks at the goal and the observations so far and picks the next action."""
    def next_action(self, goal, scratch):
        done = [s["action"] for s in scratch]
        if "profit_by" not in done: return {"thought": "First find where we lose money.", "action": "profit_by", "args": {"dim": "sub_category"}}
        worst = scratch[0]["observation"].iloc[0]["sub_category"]
        if "trend" not in done: return {"thought": f"{worst} is the biggest loss-maker. Is it getting worse?", "action": "trend", "args": {"sub_category": worst}}
        if "discount_effect" not in done: return {"thought": f"Check whether discounts explain the {worst} losses.", "action": "discount_effect", "args": {"sub_category": worst}}
        d = scratch[2]["observation"].set_index("band")["margin"]
        return {"thought": "I have enough evidence.", "final": f"{worst} lost ₹{abs(scratch[0]['observation'].iloc[0]['profit_m'])}M in 2025. Margin is {d.get('0%')}% without discount "
                f"but {d.get('>20%')}% when discounts exceed 20%. Recommendation: cap {worst} discounts at 20% and review pricing."}
def run_agent(goal, brain, max_steps=6):
    scratch = []
    for step in range(1, max_steps + 1):
        decision = brain.next_action(goal, scratch)
        print(f"step {step} THINK: {decision['thought']}")
        if "final" in decision: return decision["final"]
        obs = TOOLS[decision["action"]](**decision["args"])
        print(f"        ACT: {decision['action']}({decision['args']}) → {len(obs)} rows; first: {obs.iloc[0].to_dict()}")
        scratch.append({"action": decision["action"], "args": decision["args"], "observation": obs})
    return "Stopped: step limit reached without an answer."
print("\nFINAL:", run_agent("Why is our furniture business losing money and what should we do?", Brain()))

  2. Value: does the outcome justify extra cost and latency?

The problem MCP solves

Before MCP, every AI app needed custom code for every integration: N apps × M tools connectors. MCP (introduced by Anthropic in November 2024, now an open standard supported across Claude, ChatGPT, Gemini, Microsoft Copilot, VS Code, Cursor and many others) defines one protocol: build a server once, and every MCP-capable assistant can use it, like a USB-C port for AI.

Role What it is Example
Host The AI application the user works in Claude Desktop, Claude Code, VS Code, a custom chatbot
Client Connector inside the host, one per server Created by the host
Server A program exposing capabilities "NovaMart sales" server, GitHub, Slack, Postgres, Google Drive

The three primitives

Primitive Controlled by Purpose Example
Tools The model (with user approval) Actions and computations run_sql, create_ticket, send_email
Resources The application/user Read-only context the host can attach A policy document, a table schema, a file
Prompts The user Reusable prompt templates (often shown as slash commands) /monthly-review, /explain-query

Clients can also offer capabilities to servers, such as sampling (the server asks the host's model to generate text) and elicitation (the server asks the user for input).

Build an MCP server

The official Python SDK makes a server a few decorated functions. Type hints and docstrings become the tool schema and description.

import asyncio, json, duckdb, pandas as pd
from mcp import Client
from mcp.server.mcpserver import MCPServer        # in MCP SDK 1.x this class was FastMCP (from mcp.server.fastmcp import FastMCP)
from mcp.server.mcpserver.exceptions import ToolError
import logging; logging.getLogger("mcp").setLevel(logging.CRITICAL)      # keep the demo output tidy

sales = pd.read_csv("superstore_sales.csv", parse_dates=["order_date"])
con = duckdb.connect(); con.register("sales", sales)
server = MCPServer("NovaMart sales analytics")

@server.tool()
def sales_summary(year: int, dimension: str = "region") -> list[dict]:
    """Total sales, profit and margin for one year, grouped by region, category, segment or sub_category."""
    if dimension not in {"region", "category", "segment", "sub_category"}:
        raise ToolError("dimension must be one of region, category, segment, sub_category")   # a clear message the model can act on
    q = f"""SELECT {dimension}, ROUND(SUM(sales)/1e6, 2) AS sales_m, ROUND(SUM(profit)/1e6, 2) AS profit_m,
            ROUND(100*SUM(profit)/SUM(sales), 1) AS margin_pct FROM sales WHERE YEAR(order_date) = ? GROUP BY 1 ORDER BY sales_m DESC"""
    return con.execute(q, [year]).df().to_dict("records")

@server.tool()
def top_products(category: str, n: int = 5) -> list[dict]:
    """The n most profitable products in a category (Furniture, Office Supplies, Technology)."""
    q = "SELECT product_name, ROUND(SUM(profit)) AS profit FROM sales WHERE category = ? GROUP BY 1 ORDER BY 2 DESC LIMIT ?"
    return con.execute(q, [category, min(n, 20)]).df().to_dict("records")

@server.resource("schema://sales")
def sales_schema() -> str:
    """Column names and types of the sales table."""
    return sales.dtypes.astype(str).to_json()

@server.prompt()
def monthly_review(month: str) -> str:
    """Prompt template for a monthly business review."""
    return f"Using the sales tools, write a monthly business review for {month}: headline numbers, three drivers, one risk and one action. Cite every number's source."

Why evaluation is the core skill

LLM outputs vary with wording, model version and input. Without measurement, "it looked good in my three tests" becomes a production incident. Eval-driven development: define what good looks like, build a test set, measure every change.

Adversarial cases Prompt injection, requests for disallowed content, PII

Start with 30–100 labelled examples; grow it as you find failures. Keep a held-out set you do not tune on.

PII = {"aadhaar": r"\b[2-9]\d{3}\s?\d{4}\s?\d{4}\b", "pan": r"\b[A-Z]{5}\d{4}[A-Z]\b", "phone": r"(?:\+91[\s-]?)?\b[6-9]\d{4}[\s-]?\d{5}\b",
       "email": r"[\w.+-]+@[\w-]+(?:\.[\w-]+)+", "upi": r"\b[\w.-]+@(?:ok\w+|ybl|paytm|upi|axl|ibl)\b", "card": r"\b(?:\d{4}[\s-]?){3}\d{4}\b"}
def redact(text):
    found = {}
    for kind in ["upi", "email", "card", "aadhaar", "pan", "phone"]:                 # order matters: UPI ids look like emails
        for m in re.findall(PII[kind], text): found.setdefault(kind, []).append(m)
        text = re.sub(PII[kind], f"[{kind.upper()}]", text)
    return text, found

POLICY_BLOCK = [r"guaranteed? returns?", r"\b100% safe\b", r"medical (advice|diagnosis)", r"\bpassword\b"]
def check_output(answer, allowed_facts=None, max_words=120):
    issues = []

    return issues or ["ok"]

Handling refusals and failures

Models sometimes decline (safety) or fail (timeouts, invalid JSON). Plan for it: check stop_reason ("refusal", "max_tokens"), retry with backoff, fall back to a rule or a human queue, and show the user a helpful message. Never silently drop items in a batch.

Red-teaming

Before launch, try to break the system the way attackers and confused users would: injections in uploaded files and retrieved pages, jailbreak role-play, requests for other customers' data, harmful advice, very long inputs, multilingual tricks. Use the OWASP Top 10 for LLM Applications (prompt injection, sensitive information disclosure, supply chain, data poisoning, improper output handling, excessive agency, system prompt leakage, vector/embedding weaknesses, misinformation, unbounded consumption) as a checklist.

Full fine-tuning vs LoRA

Full fine-tuning updates every weight: billions of parameters, lots of GPU memory. LoRA (low-rank adaptation) freezes the original weights and learns a small update for selected matrices as the product of two thin matrices:

Python
def lora_params(d, k, r): return r * (d + k)
d = k = 4096                                                   # one attention projection in a ~7–8B model
for r in (4, 8, 16, 64):
    print(f"rank {r:2d}: {lora_params(d, k, r):,} trainable vs {d * k:,} full ({100 * lora_params(d, k, r) / (d * k):.2f}%)")
layers, mats = 32, 4                                           # 32 transformer layers × q, k, v, o projections
total_full = 8e9; total_lora = layers * mats * lora_params(4096, 4096, 16)
print(f"whole model: LoRA r=16 trains {total_lora / 1e6:.1f}M parameters ≈ {100 * total_lora / total_full:.2f}% of 8B")
print(f"memory for weights in 16-bit: {total_full * 2 / 1e9:.0f} GB | 4-bit (QLoRA): {total_full * 0.5 / 1e9:.0f} GB")

Python
rng = np.random.default_rng(0)
true_update = rng.normal(size=(64, 4)) @ rng.normal(size=(4, 64))           # a genuinely low-rank change
U, S, Vt = np.linalg.svd(true_update + rng.normal(0, .01, (64, 64)))
for r in (1, 2, 4, 8):
    approx = (U[:, :r] * S[:r]) @ Vt[:r]
    print(f"rank-{r} approximation keeps {100 * (1 - np.linalg.norm(true_update - approx) / np.linalg.norm(true_update)):.1f}% of the update with {r * 128} numbers instead of 4,096")

Distillation: big teacher, small student

Use a large model to label or generate high-quality training data, then fine-tune a small, cheap model on it. For a narrow, high-volume task (classifying millions of tickets), the student can approach the teacher's accuracy at a fraction of the cost and latency.

Python
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import make_pipeline
from sklearn.metrics import accuracy_score

for name, labels in [("human labels", train.sentiment), ("teacher (LLM) labels", noisy.sentiment)]:

Python
FORBIDDEN = r"\b(insert|update|delete|drop|alter|create|replace|copy|attach|detach|pragma|install|load|export)\b"
def safe_execute(sql_text, max_rows=200):
    sql_text = sql_text.strip().strip("`").removeprefix("sql").strip().rstrip(";")
    if ";" in sql_text: raise ValueError("multiple statements are not allowed")
    if not re.match(r"^(with|select)\b", sql_text, re.I): raise ValueError("only SELECT/WITH queries are allowed")
    if re.search(FORBIDDEN, sql_text, re.I): raise ValueError("forbidden keyword")
    return con.execute(f"SELECT * FROM ({sql_text}) LIMIT {max_rows}").df()
print(safe_execute("```sql\nSELECT region, ROUND(100*SUM(profit)/SUM(sales), 2) AS margin FROM sales WHERE YEAR(order_date)=2025 GROUP BY 1 ORDER BY 2 DESC\n```"))

    try: safe_execute(bad)
    except ValueError as e: print("blocked:", bad, "→", e)

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field
import anthropic, time, logging
app, client = FastAPI(), anthropic.Anthropic()
SESSIONS: dict[str, list] = {}                         # use Redis or a database in production
class ChatIn(BaseModel):
    session_id: str = Field(max_length=64)
    message: str = Field(min_length=1, max_length=2000)
@app.post("/chat")
def chat(body: ChatIn):
    if injection_score(body.message)[0] >= 2: raise HTTPException(400, "Please rephrase your question.")
    prompt, ctx = build_prompt(body.message)            # RAG from lesson 5
    history = SESSIONS.setdefault(body.session_id, [])[-6:]          # keep the last 3 exchanges
    t0 = time.perf_counter()
    resp = client.messages.create(model="claude-sonnet-5-5", max_tokens=2000, system=[{"type": "text", "text": SYSTEM, "cache_control": {"type": "ephemeral"}}],
                                  messages=history + [{"role": "user", "content": prompt}])
    answer = next(b.text for b in resp.content if b.type == "text")
    issues = check_output(answer)                        # lesson 9 guardrails
    if issues != ["ok"]: answer = "Let me connect you with a support agent."
    SESSIONS[body.session_id] = history + [{"role": "user", "content": body.message}, {"role": "assistant", "content": answer}]
    logging.info({"latency_ms": int(1000 * (time.perf_counter() - t0)), "in": resp.usage.input_tokens, "out": resp.usage.output_tokens, "issues": issues})
    return {"answer": answer, "sources": ctx.id.tolist()}

Cost and capacity planning

Python
import pandas as pd, numpy as np
PRICE = {"claude-haiku-5-5": (0.10, 0.50), "claude-sonnet-5-5": (2.00, 10.00), "claude-opus-5-5": (4.00, 20.00)}   # USD per million tokens, Oct 2026 list prices
def monthly(conversations, turns, system_tok, ctx_tok, user_tok, out_tok, model, cache_hit=0.0, usd_inr=88):
    pin, pout = PRICE[model]; calls = conversations * turns
    cached = system_tok * cache_hit; uncached = system_tok - cached + ctx_tok + user_tok
    usd = calls * ((uncached * pin + cached * pin * 0.1) + out_tok * pout) / 1e6
    return round(usd * usd_inr)
base = dict(conversations=60_000, turns=4, system_tok=1500, ctx_tok=1200, user_tok=60, out_tok=180)
rows = []
for m in PRICE:
    for hit in (0.0, 0.9):
        rows.append({"model": m, "system prompt cache hit": f"{hit:.0%}", "₹ / month": monthly(model=m, cache_hit=hit, **base)})
plan = pd.DataFrame(rows); print(plan.to_string(index=False))
route = 0.8 * monthly(model="claude-haiku-5-5", cache_hit=.9, **base) + 0.2 * monthly(model="claude-sonnet-5-5", cache_hit=.9, **base)

Launch checklist

  1. Eval set passes target scores; regression suite in CI.
  2. Guardrails: injection, PII, scope, output validation, refusal handling; human handover path.
  3. Security: secrets in a vault, least-privilege tools, authentication, rate limits.
  4. Privacy: DPDP Act notice and consent, retention limits, provider data settings.
  5. Cost and latency budgets with alerts; kill switch and rollback to the previous prompt.
  6. Monitoring dashboards and an on-call owner.
  7. Documentation: model card / system card, known limitations, escalation contacts.
  8. Gradual rollout (internal → 5% → 50% → 100%) with an A/B comparison against the old process.

Responsible AI governance

Be transparent that users are talking to AI; keep humans accountable for consequential decisions (refunds, credit, hiring); test for bias across languages and customer groups; follow emerging regulation (India's DPDP Act and IT rules, the EU AI Act for EU users, sector rules such as RBI guidelines); and keep an incident process for harmful outputs.

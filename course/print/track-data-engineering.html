What Data Engineering Is, Its Roles and the Data Formats It Uses

Understand what data engineers build, the path data takes from source to report, and the file formats used to store and move it (CSV, JSON, XML, Parquet, Avro and ORC), with the trade-offs in size, speed and schema that decide which to use.

By the end of this lesson you can
  • Describe the data engineering role and how it differs from analytics and data science
  • Trace data from a source system to a trusted reporting table
  • Compare CSV, JSON, XML, Parquet, Avro and ORC on size, speed, schema and readability
  • Choose a file format for a given job, with reasons

What data engineering is

Data engineering builds and runs the systems that move, store and prepare data, so that analysts, data scientists and AI applications can use it reliably. Without reliable pipelines, a dashboard shows wrong numbers and a model trains on stale data. The data engineer is responsible for that reliability.

Case studyThe order that never reached the dashboard

A sales app writes orders to a database. A nightly job should copy them to a warehouse, so that the Monday revenue dashboard is correct. One Sunday the job silently skipped a file. The dashboard showed a 9% drop that nobody could explain for two days. Data engineering exists to make that failure impossible to hide and fast to fix.

The path data takes

Sources (apps, databases, APIs, files)
   └─► Ingestion: copy raw data into a landing zone
         └─► Storage: keep raw copies, cleaned data and reporting tables
               └─► Transformation: clean, join, model, aggregate
                     └─► Serving: trusted tables for analysts, models and apps
                           └─► Consumers: Power BI, notebooks, AI features

Every arrow is a point where data can be lost, duplicated or delayed. Most of data engineering is making those arrows reliable and visible.

Roles around the data

Role Main work Typical tools
Data engineer Pipelines, storage, reliability, performance SQL, Python, Spark, Airflow, dbt, cloud services
Analytics engineer Modelled tables and tested transformations for analysts SQL, dbt, a warehouse
Data analyst Questions, dashboards, reports SQL, Excel, Power BI
Data scientist Models and experiments Python, statistics, ML libraries
Platform engineer The infrastructure the others run on Cloud, containers, infrastructure as code

In a small team one person may do several roles. The distinction matters because each role needs different guarantees: an engineer must make loads correct and repeatable; an analyst must trust the meaning of each column.

File formats

A file format decides how data is laid out on disk. It affects size, how fast it can be read, whether a schema is stored with it, and whether people can open it in a text editor.

Format Type Schema stored? Strength Weakness Typical use
CSV Text, rows No Universal, readable No types, slow, large Exports and small files
JSON Text, nested No (implicit) Nested and flexible Verbose, slow for big data APIs and event payloads
XML Text, nested tags Optional Standard in some industries Very verbose Legacy and exchange formats
Parquet Binary, columnar Yes Small, fast for analysis Not human-readable Analytics storage
Avro Binary, row-based Yes (in the file) Schema evolution, streaming Less efficient for analytics Event streams and messages
ORC Binary, columnar Yes Compact, fast for analytics Mainly used in the Hadoop world Big-data warehouses

Columnar formats (Parquet, ORC) store each column together. An analytics query that needs two columns from a hundred reads only those two. Row-based formats (CSV, Avro) store each record together, which suits writing and streaming one record at a time.

Compression (such as Snappy or gzip) makes files smaller at the cost of some processing time. Columnar files compress very well because similar values sit next to each other.

Choosing a format

  1. Who reads it? If people open it in Excel, CSV is the practical choice.
  2. How is it queried? Analytics on large data favours Parquet or ORC.
  3. Does it change over time? Avro handles schema evolution well for event streams.
  4. Does it cross systems? Check that each consumer supports the format and its types.

::::warn CSV loses types A CSV has no record of whether 001 is a number or a code. Leading zeros disappear, dates become text, and a comma inside a field breaks the row. Store analytical data in typed formats, and keep CSV for exchange and inspection. ::::

Roles in practice: a pipeline's owner

Every pipeline needs a named owner who is paged when it fails, who reviews its changes and who answers questions about its tables. Without an owner, a pipeline becomes a silent dependency that nobody maintains.

Interview cornerWhat is the difference between a data engineer and a data analyst?

The analyst answers questions with data that already exists in trusted tables. The engineer makes sure those tables exist, are correct, are refreshed on time and are recoverable when something breaks. The analyst asks what happened; the engineer makes sure the answer is right.

::::key What to remember - Data engineering builds the reliable path from source to trusted tables. - Know the roles: engineer, analytics engineer, analyst, scientist and platform engineer. - Choose formats by reader, query pattern, schema needs and cross-system support. - Columnar formats suit analytics; row formats suit streams; CSV suits inspection. - Every pipeline needs an owner. ::::

What ingestion is

Ingestion copies data from a source into the platform's landing zone without changing its meaning. The landing zone is the first place the data lives on your side: a bucket, a folder or a raw table. Keeping an unchanged copy makes every later step repeatable, because you can rebuild the rest from it.

Case studyThree sources, three ways in

A retailer needs sales from its point-of-sale files (delivered as daily CSVs), its online store (a REST API with new orders) and its inventory database (changes must appear within the hour). The same platform needs three ingestion methods. Choosing wrongly means either stale data or a source overloaded by constant queries.

The five methods

Method How it works Freshness Load on source Typical use
Batch Copy everything, or a period, at intervals Hours to days Periodic and heavy Daily files, full table dumps
Streaming Events are sent as they happen Seconds Low per event Clicks, sensor data, payments
API pull Call an endpoint, page through results Minutes to hours Depends on rate limits SaaS tools, partner data
File drop A system places files in a folder or bucket Per drop Low Vendor exports, reports
Database extract Query a table for rows changed since a point Minutes to hours Query load on the database Operational tables
Change data capture (CDC) Read the database's change log Seconds to minutes Very low Keeping a warehouse close to live

Incremental pulls with a watermark

Copying everything every time is expensive. An incremental pull fetches only rows changed since the last successful run. The last value seen (the watermark, often an updated_at timestamp) is stored in a control table and advanced only after the load succeeds.

Python
import pandas as pd
import duckdb

con = duckdb.connect()
source = pd.read_csv("daily_sales.csv", parse_dates=["date"]).rename(columns={"date": "updated_at"})
con.register("source_rows", source)

# Control table: one row per source, holding the last watermark that loaded successfully
con.execute("CREATE TABLE IF NOT EXISTS load_control (source VARCHAR PRIMARY KEY, watermark TIMESTAMP)")
con.execute("CREATE TABLE IF NOT EXISTS landing_sales (updated_at TIMESTAMP, units_sold BIGINT)")

def incremental_load(con, source_name, cutoff):
    wm = con.execute("SELECT watermark FROM load_control WHERE source = ?", [source_name]).fetchone()
    last = wm[0] if wm else pd.Timestamp("1900-01-01")
    new = con.execute("SELECT * FROM source_rows WHERE updated_at > ? AND updated_at <= ?",
                      [last, cutoff]).fetchdf()
    con.register("batch", new)
    con.execute("INSERT INTO landing_sales SELECT updated_at, units_sold FROM batch")
    new_wm = new["updated_at"].max() if len(new) else last
    con.execute("INSERT OR REPLACE INTO load_control VALUES (?, ?)", [source_name, new_wm])
    return len(new), new_wm

print(incremental_load(con, "pos_daily", pd.Timestamp("2025-01-31")))
print(incremental_load(con, "pos_daily", pd.Timestamp("2025-01-31")))   # rerun: loads nothing new
print(con.execute("SELECT COUNT(*) FROM landing_sales").fetchone())
Output
(1127, Timestamp('2025-01-31 00:00:00'))
(0, datetime.datetime(2025, 1, 31, 0, 0))
(1127,)

The second run loads nothing, because the watermark already covers that period. The watermark moves only when the load succeeds, so a failed run leaves it where it was and the next run retries the same rows. The rerun safety here is the same idea as the idempotent loads in the SQL lessons.

::::warn Watermarks on event time can miss late rows A row dated yesterday that arrives today is skipped by a watermark on the event date. Use the time the record was written or updated when the source provides it, or re-load a short safety window and deduplicate. ::::

Paging through an API

APIs rarely return everything at once. They return pages, often with a cursor or a next link. The ingestion code must follow every page, handle rate limits, and stop only when the source says there is nothing left.

Python
# Illustrative pattern (not run: needs a live API). Replace the URL and field names
# with the source's documentation.
import time
import requests

def fetch_all(url, token, page_size=100, max_retries=5):
    headers = {"Authorization": f"Bearer {token}"}
    cursor, rows = None, []
    while True:
        params = {"limit": page_size}
        if cursor:
            params["cursor"] = cursor
        for attempt in range(max_retries):
            resp = requests.get(url, headers=headers, params=params, timeout=30)
            if resp.status_code == 429:               # rate limited: wait, then retry
                time.sleep(2 ** attempt)
                continue
            resp.raise_for_status()
            break
        body = resp.json()
        rows.extend(body["data"])
        cursor = body.get("next_cursor")
        if not cursor:
            return rows                                # no more pages: stop

Every API has its own limits and paging style. Read the documentation before writing the loop, and record how many rows each run fetched so that a silent change in page size is visible.

Streaming and deduplication

Streaming sources can deliver the same event twice (for example, after a network retry). Deduplicate on a unique event identifier, not on the whole row, because two genuine events can look identical.

Python
import pandas as pd

events = pd.DataFrame({
    "event_id": ["e1", "e2", "e2", "e3"],          # e2 was delivered twice
    "order_id": ["A10", "A11", "A11", "A12"],
    "amount":   [120.0, 80.0, 80.0, 45.0],
})
unique_events = events.drop_duplicates(subset=["event_id"], keep="last")
print(unique_events)
print("duplicates removed:", len(events) - len(unique_events))
Output

0       e1      A10   120.0
2       e2      A11    80.0
3       e3      A12    45.0

Change data capture

CDC reads the database's own log of inserts, updates and deletes, instead of querying the tables. It sees every change, including deletes that a query would miss, and it puts little load on the database.

Approach Sees deletes? Sees every change? Load on source
Query by updated_at No (deleted rows vanish) Only if the column is reliable Query load
Full reload Yes, by comparison Yes, but slowly Heavy
CDC from the log Yes Yes Very low

CDC needs access to the database log and careful handling of schema changes: when a column is added, the capture must know about it before the next change arrives. Tools built for this exist; check the documentation of the database and tool you choose.

Landing zone rules

  • Store the raw copy unchanged, with the load time and source name attached.
  • Keep one load record per run: source, rows read, rows written, watermark, status.
  • Never transform data on the way in; transform in the next layer.
  • Keep raw data long enough to rebuild the layers above it.
Interview cornerHow would you ingest data from a source that has no timestamp column?

Options: a full reload with a comparison of keys to find inserts, updates and deletes, if the table is small; CDC from the database log, if access is available; or a trigger that writes changes to an audit table. State the trade-off: full reloads are simple but heavy, CDC is precise but needs access and maintenance.

::::key What to remember - Pick ingestion by freshness, volume and what the source allows. - Incremental loads use a watermark that moves only after success. - Follow every page of an API and respect its rate limits. - Deduplicate streams on a unique event ID. - CDC captures deletes and changes with little load, but needs access and schema care. ::::

ETL versus ELT and Pipeline Reliability: Idempotency, Retries and Incremental Loads

ETL and ELT

ETL (extract, transform, load) cleans and reshapes data in a separate processing step, then loads the result. ELT (extract, load, transform) loads the raw data first, then transforms it inside the warehouse. The difference is where the work happens and what is kept.

Question Favours ETL Favours ELT
Must sensitive data be masked before it lands? Yes No, if the warehouse can restrict access
Is the warehouse elastic and cheap to compute? Less relevant Yes
Must raw data be kept for rebuilds? Less often Yes
Are many teams building different views of the same raw data? No Yes
Is the transformation complex and not SQL-friendly? Yes Harder
Case studyMasking before the warehouse

A bank's card transactions include full card numbers. The warehouse is shared with many teams. The pipeline must replace the card numbers with a token before anything is written to the warehouse. That is an ETL requirement: the transformation happens before the load, so raw card numbers never land.

Most modern cloud teams use ELT for analytics and ETL for sensitive or complex steps. Both are valid; the choice is a decision about where the risk and the cost should sit.

Idempotency: the property that makes reruns safe

An operation is idempotent when running it again gives the same final result. Pipelines rerun all the time: after a failure, after a fix, or when a scheduler fires twice. A load that simply appends rows doubles the totals on every rerun. Two patterns make a load idempotent:

  1. Overwrite by partition. Each run rewrites the partition it covers (for example, one day). Rerunning the same day replaces the same rows.
  2. Merge on a key. Each row has a stable key; the load updates existing keys and inserts new ones.
Python
import pandas as pd
import duckdb

con = duckdb.connect()
sales = pd.read_csv("daily_sales.csv", parse_dates=["date"])
con.register("sales", sales)
con.execute("CREATE TABLE fact_daily AS SELECT * FROM sales WHERE 1 = 0")

def load_partition(con, day):
    """Overwrite exactly one day's partition, so reruns cannot double it."""
    con.execute("DELETE FROM fact_daily WHERE date = ?", [day])
    con.execute("INSERT INTO fact_daily SELECT * FROM sales WHERE date = ?", [day])
    return con.execute("SELECT COUNT(*) FROM fact_daily WHERE date = ?", [day]).fetchone()[0]

print("first run:", load_partition(con, "2025-01-06"))
print("rerun:    ", load_partition(con, "2025-01-06"))     # same result, not doubled
print("total rows:", con.execute("SELECT COUNT(*) FROM fact_daily").fetchone()[0])
Output
first run: 1
rerun:     1
total rows: 1

The rerun reports the same count, and the table holds one copy of each day. Compare that with a plain INSERT run twice, which would double the day.

Retries: bounded, backed off and selective

Some failures are temporary (a network timeout, a database that is briefly busy). Retrying them is correct. Other failures are permanent (a missing column, a bad credential) and retrying them wastes time and can hide the cause. A retry policy needs three rules:

  • Bounded: a fixed number of attempts, then fail loudly.
  • Backed off: wait longer between attempts (1, 2, 4 seconds), so the system can recover.
  • Selective: retry only errors that can be temporary.
Python
import time

def with_retries(fn, attempts=4, base_delay=0.01, retryable=(TimeoutError, ConnectionError)):
    for i in range(attempts):
        try:
            return fn()
        except retryable:
            if i == attempts - 1:
                raise                                   # give up and surface the error
            time.sleep(base_delay * (2 ** i))
        # any other exception is not retried: it is a permanent error

calls = {"n": 0}
def flaky_load():
    calls["n"] += 1
    if calls["n"] < 3:
        raise TimeoutError("warehouse busy")
    return "loaded"

print(with_retries(flaky_load), "after", calls["n"], "attempts")
Output
loaded after 3 attempts

A schema error or a permission error is not in the retryable list, so it fails immediately with its real message. The retry is for the transient failure only.

::::warn Do not retry non-idempotent writes blindly Retrying a write that may have partly succeeded can duplicate it. Pair retries with idempotent loads (partition overwrite or merge on key), or with a check that asks whether the write already happened. ::::

Incremental loads and state

An incremental pipeline keeps a small piece of state: the watermark from the ingestion lesson, and the last successful partition. Store the state only after the data is committed, so a crash between the two leaves the state behind the data, and the next run safely reprocesses rather than skipping.

Reconciliation: prove the load is complete

A load that finishes without an error is not necessarily correct. Reconciliation compares the target with the source: row counts, sums of key measures, and distinct key counts, per partition.

Python
src = sales[sales["date"] == "2025-01-06"]
tgt = con.execute("SELECT * FROM fact_daily WHERE date = '2025-01-06'").fetchdf()

checks = {
    "row count": (len(src), len(tgt)),
    "units total": (int(src["units_sold"].sum()), int(tgt["units_sold"].sum())),
}
for name, (expected, actual) in checks.items():
    status = "PASS" if expected == actual else "FAIL"
    print(f"{status}  {name}: source={expected} target={actual}")
Output
PASS  row count: source=1 target=1
PASS  units total: source=297 target=297

Run reconciliation after every load, store the results, and alert on any failure. A mismatch is the earliest and cheapest sign of a bad load.

A reliability checklist

  • [ ] Each load is idempotent: a rerun gives the same result.
  • [ ] Retries are bounded, backed off and limited to transient errors.
  • [ ] State (watermark, last partition) advances only after a commit.
  • [ ] Reconciliation runs after every load, with stored results.
  • [ ] Failures alert a named owner with the partition and the error.
  • [ ] A rerun procedure is written down and has been tested.
Interview cornerWhat makes a pipeline safe to rerun?

Each run writes to a deterministic target: it overwrites the partition it owns or merges on a key, so the same input always produces the same output. Retries cover only transient errors, state advances after the commit, and reconciliation proves the result. Those four together are what make rerunning a routine action rather than a risk.

::::key What to remember - ETL transforms before loading; ELT loads raw data and transforms in the warehouse. Choose by risk, cost and rebuild needs. - Idempotency means a rerun gives the same result: overwrite partitions or merge on keys. - Retry only transient errors, with a limit and backoff. - Advance state only after commit, and reconcile every load against its source. ::::

Three levels of model

A data model describes what the data means and how it is stored. Designers work at three levels:

Level Question it answers Contents Audience
Conceptual What are the things the business cares about? Entities (customer, order, product) and relationships Business and analysts
Logical What information does each entity hold? Attributes, keys, relationships, rules, no technology Analysts and engineers
Physical How is it stored in this database? Tables, types, indexes, partitions Engineers

Start at the conceptual level with the business, move to logical, and finish at physical. A physical model built without the business concepts stores what the source happens to contain, not what the business needs.

Star and snowflake schemas

A fact table records measurable events (a sale, a shipment, a payment) with numeric measures and keys to the dimensions. A dimension table describes the context (who, what, where, when). A star schema keeps each dimension flat, with one table per dimension. A snowflake schema normalises dimensions into sub-tables.

Star:                                   Snowflake:
   dim_customer ─┐                         dim_customer ─► dim_segment
   dim_product  ─┼─► fact_sales            dim_product  ─► dim_category ─► dim_department
   dim_date     ─┤                         dim_date     ─┘
   dim_store    ─┘                         dim_store
Star Snowflake
Query simplicity Simple, fewer joins More joins
Storage Some repetition in dimensions Less repetition
Typical use Reporting and BI Very large or shared hierarchies
Maintenance One table per dimension Many small tables

Most reporting warehouses use stars, because the cost of repeating a few text values is small and the queries are much easier to write and understand.

Surrogate keys

A surrogate key is a system-generated integer with no business meaning. Facts point to surrogates, not to source keys. This keeps joins small and fast, and insulates the warehouse from source changes (a customer's email can change; the surrogate key does not).

Building a star schema

The block below builds a customer dimension with a surrogate key and a fact table pointing to it, from the course's customer and sales data.

Python
import pandas as pd
import duckdb

con = duckdb.connect()
customers = pd.read_csv("customers.csv")
sales = pd.read_csv("superstore_sales.csv", parse_dates=["order_date"])
con.register("customers_src", customers)
con.register("sales_src", sales)

con.execute("""
    CREATE TABLE dim_customer AS
    SELECT ROW_NUMBER() OVER (ORDER BY customer_id) AS customer_key,
           customer_id, customer_name, segment, region
    FROM customers_src
""")
con.execute("""
    CREATE TABLE fact_sales AS
    SELECT s.row_id AS sale_id, d.customer_key, s.order_date, s.sales, s.profit, s.quantity
    FROM sales_src s

Slowly changing dimensions

Dimensions change: a customer moves region, changes segment, or changes name. The question is what the reports should show. The answer is an SCD type.

Type Behaviour History kept? Use when
Type 1 Overwrite the old value No Corrections, where the old value was wrong
Type 2 Add a new row with validity dates and a current flag Yes, full The business needs history as it was at the time
Type 3 Add a column for the previous value One previous value only Only the last change matters

SCD Type 1: overwrite

Python
dim = pd.DataFrame({"customer_id": ["C1"], "region": ["North"]})
# The region was keyed wrongly: overwrite it in place, keeping no history
dim.loc[dim["customer_id"] == "C1", "region"] = "South"
print(dim)

Type 1 loses the old value. Use it only when the old value was an error.

SCD Type 2: keep history

Type 2 closes the old row and inserts a new one, so that every fact joins to the version that was current on its date.

Python
import pandas as pd

dim = pd.DataFrame([
    {"customer_key": 1, "customer_id": "C1", "region": "North",
     "valid_from": pd.Timestamp("2024-01-01"), "valid_to": pd.Timestamp("9999-12-31"), "is_current": True},
])
next_key = dim["customer_key"].max() + 1

def apply_scd2(dim, customer_id, new_region, change_date):
    global next_key
    current = dim[(dim["customer_id"] == customer_id) & dim["is_current"]]
    if current.empty or current.iloc[0]["region"] == new_region:
        return dim                                      # no change: nothing to do
    idx = current.index[0]
    dim.loc[idx, "valid_to"] = change_date - pd.Timedelta(days=1)
    dim.loc[idx, "is_current"] = False
    new_row = {"customer_key": next_key, "customer_id": customer_id, "region": new_region,
               "valid_from": change_date, "valid_to": pd.Timestamp("9999-12-31"), "is_current": True}
    next_key += 1
    return pd.concat([dim, pd.DataFrame([new_row])], ignore_index=True)

dim = apply_scd2(dim, "C1", "South", pd.Timestamp("2025-06-01"))
dim = apply_scd2(dim, "C1", "South", pd.Timestamp("2025-06-01"))   # rerun: no duplicate version
print(dim)
Output
   customer_key customer_id region valid_from             valid_to  is_current
0             1          C1  North 2024-01-01  2025-05-31 00:00:00       False
1             2          C1  South 2025-06-01  9999-12-31 00:00:00        True

The rerun creates no duplicate, because the current row already has the new region. A fact dated March 2025 joins to the North version (key 1); a fact dated July 2025 joins to the South version (key 2). That is what "as it was at the time" means.

Interview cornerWhen would you use Type 2 rather than Type 1?

When the business needs reports to reflect the attribute as it was at the time of each event: a customer's region for sales, a product's price band for margin, an employee's department for headcount history. Type 1 is for corrections of errors, not for real changes.

Data Warehouses, Data Marts, Data Lakes, Lakehouses and the Medallion Architecture

Understand the storage choices behind a data platform: warehouse, data mart, data lake and lakehouse. Build a bronze, silver and gold (medallion) layering in code, with a quality gate between layers and a clear rule for what each layer is allowed to contain.

  • Explain the medallion architecture and what each layer holds

Four storage patterns

Pattern What it holds Strength Weakness Typical user
Data warehouse Structured, modelled tables for reporting Fast SQL, governance, trust Costly for raw or unstructured data Analysts and finance
Data mart A subject-area slice of the warehouse (sales, HR) Focused, easy to use Can duplicate and drift if not governed One department
Data lake Raw files of any type on cheap storage Cheap, flexible, keeps everything Easy to become a swamp of untrusted files Engineers and data scientists
Lakehouse Open table formats on lake storage, with transactions and schemas One copy serves analytics and machine learning Requires careful table management Mixed teams

A data mart is usually a set of tables taken from a warehouse for one team. A data lake is cheap storage that accepts files without a schema; without discipline it fills with duplicate and undocumented data. A lakehouse adds table features (transactions, schema enforcement, time travel) to lake storage, so one copy can serve both dashboards and model training.

Case studyA lake that nobody trusts

A company dumps every export into one storage bucket. Three years later, nobody knows which of the nine "sales" folders is current, and two dashboards disagree by 4%. The fix is not a bigger bucket; it is layers with rules: raw data kept as it arrived, cleaned data with checked types, and reporting tables that the business has agreed on.

The medallion architecture

The medallion architecture organises a lakehouse or warehouse into three layers, each with a stricter contract than the one before:

Layer Contents Rules Who reads it
Bronze Raw data as it arrived, with load time and source No changes; append-only Engineers (for rebuilds)
Silver Cleaned, typed, deduplicated, conformed data Types checked; keys unique; quality gate passed Engineers and analysts
Gold Business tables and metrics for reporting Agreed definitions; documented; tested Business users, dashboards, AI features

Each layer can be rebuilt from the one below it. If a gold table is wrong, you fix the transformation and rebuild gold; you do not patch the table by hand.

Building the layers

The block below builds bronze, silver and gold from the superstore file, with a quality gate between silver and gold. The bronze layer keeps the raw rows unchanged.

Python
import pandas as pd
import duckdb

con = duckdb.connect()
raw = pd.read_csv("superstore_sales.csv", parse_dates=["order_date", "ship_date"])

# Bronze: the raw rows, unchanged, with load metadata
bronze = raw.copy()
bronze["_loaded_at"] = pd.Timestamp("2026-01-15 06:00")
bronze["_source"] = "superstore_sales.csv"
con.register("bronze_src", bronze)
con.execute("CREATE TABLE bronze_sales AS SELECT * FROM bronze_src")

# Silver: typed, deduplicated on the line key, with obvious bad rows removed
con.execute("""
    CREATE TABLE silver_sales AS
    SELECT DISTINCT ON (row_id)
           row_id, order_id, order_date, ship_date, customer_id, product_id,
           CAST(sales AS DOUBLE) AS sales, CAST(profit AS DOUBLE) AS profit,
           CAST(quantity AS INTEGER) AS quantity, region, category
    FROM bronze_sales
    WHERE sales IS NOT NULL AND quantity > 0
    ORDER BY row_id
""")

# Quality gate: the gate must pass before gold is built
gate = con.execute("""
    SELECT
      (SELECT COUNT(*) FROM bronze_sales) AS bronze_rows,
      (SELECT COUNT(*) FROM silver_sales) AS silver_rows,
      (SELECT COUNT(*) FROM silver_sales WHERE row_id IS NULL) AS null_keys,
      (SELECT COUNT(*) - COUNT(DISTINCT row_id) FROM silver_sales) AS duplicate_keys
""").fetchdf()
print(gate)
assert gate["null_keys"][0] == 0 and gate["duplicate_keys"][0] == 0, "quality gate failed"

# Gold: one agreed reporting table, monthly by region and category
con.execute("""
    CREATE TABLE gold_monthly_sales AS
    SELECT DATE_TRUNC('month', order_date) AS month, region, category,
           ROUND(SUM(sales), 2) AS sales, ROUND(SUM(profit), 2) AS profit,
           SUM(quantity) AS units
    FROM silver_sales
    GROUP BY 1, 2, 3
""")
print(con.execute("SELECT * FROM gold_monthly_sales ORDER BY month LIMIT 5").fetchdf())

Which layer should a consumer read?

Consumer Read from Reason
Executive dashboard Gold Agreed definitions and tested
Analyst exploring a new question Silver Clean and typed, with detail
Data scientist building a model Silver (or a feature table derived from it) Needs detail and history
Engineer rebuilding a table Bronze The unchanged source
AI assistant answering business questions Gold for metrics, silver for detail Grounded in agreed numbers

Layer rules to write down

  1. Bronze: append-only, never edited, with load time and source on every row.
  2. Silver: one definition of each entity, types enforced, keys unique, and a documented list of rows removed and why.
  3. Gold: each table has an owner, a description, a test on its key and a stated refresh time.
  4. A table in one layer is never read by a consumer that should use another layer, unless the exception is written down.
Interview cornerWarehouse or lakehouse: which would you choose?

If the data is structured, the team is SQL-focused, and reporting is the main use, a warehouse is simpler and well governed. If the company also stores files, images or logs, and data scientists and analysts both need the same data, a lakehouse keeps one copy and serves both. Many organisations run a lakehouse for raw and mixed data and a warehouse or gold layer for reporting.

::::key What to remember - Warehouses hold modelled reporting data; lakes hold raw files; lakehouses add table features to lake storage. - Medallion layers: bronze raw and unchanged, silver cleaned and typed, gold agreed and tested. - Put a quality gate between silver and gold, and stop the build when it fails. - Each consumer reads from the layer that matches its trust and detail needs. ::::

Apache Airflow: DAGs, Tasks, Scheduling and Retries

Orchestrate a data pipeline with Apache Airflow. Define tasks and dependencies as a directed acyclic graph (DAG), schedule runs with idempotent logic, configure retries and alerts, and learn the operational habits that keep a DAG reliable.

● Gap-fill lesson✦ 2026Advanced⏱ 120 min
By the end of this lesson you can

  • Write a DAG with a schedule, retries and failure alerts
  • Keep tasks idempotent so that reruns and backfills are safe
  • Diagnose a failed run from the task logs and the run history

What Airflow does

Apache Airflow schedules and monitors workflows. It does not process the data itself: it runs the tasks you define, in the right order, at the right time, and it records what happened. A task might call a SQL script, start a Spark job, or copy a file. Airflow decides when, in what order and what to do when a step fails.

Case studyThe nightly close

Every night a pipeline must load the day's files, run quality checks, rebuild the reporting tables and then refresh the dashboard. If the quality check fails, the dashboard must not refresh. If the load fails at 02:00, the team must know by 02:05, and the rerun must not duplicate data. An orchestrator makes each of those rules explicit.

DAGs: tasks with dependencies

A DAG (directed acyclic graph) is a set of tasks with arrows between them that show what must finish first. "Directed" means the arrows have a direction; "acyclic" means no task can depend on itself. The DAG is the pipeline's blueprint.

load_files ──► quality_check ──► build_gold ──► refresh_dashboard
                    │
                    └── (on failure) alert_owner

The following DAG is written for Airflow 2.x. It is shown as code and not run, because it needs an Airflow installation and a scheduler. Check the current Airflow documentation for the exact import paths in your version.

Python
from datetime import datetime, timedelta
from airflow import DAG
from airflow.operators.bash import BashOperator
from airflow.operators.python import PythonOperator

default_args = {
    "owner": "data-engineering",
    "retries": 3,                          # retry transient failures
    "retry_delay": timedelta(minutes=5),
    "email_on_failure": True,
    "email": ["data-oncall@example.com"],
}

with DAG(
    dag_id="nightly_sales_close",
    start_date=datetime(2025, 1, 1),
    schedule="0 2 * * *",                  # every day at 02:00
    catchup=False,                         # do not run every missed day on deploy
    default_args=default_args,
    tags=["sales", "nightly"],
) as dag:
    load_files = BashOperator(task_id="load_files", bash_command="python load.py --date {{ ds }}")
    quality = PythonOperator(task_id="quality_check", python_callable=lambda: print("checks passed"))
    build_gold = BashOperator(task_id="build_gold", bash_command="python build_gold.py --date {{ ds }}")
    refresh = BashOperator(task_id="refresh_dashboard", bash_command="python refresh.py")

    load_files >> quality >> build_gold >> refresh

Read the key lines:

Line Meaning
schedule="0 2 * * *" A cron schedule: 02:00 every day
retries: 3 Retry each failing task up to three times
retry_delay Wait five minutes between tries
{{ ds }} Airflow's logical date, so each run processes its own day
catchup=False Do not replay every past day when the DAG is first deployed
>> "Must finish before": the dependency arrows

Idempotent tasks

Retries and backfills rerun tasks. A task that appends rows doubles them on every retry. Write each task so that running it for a given date twice gives the same result: overwrite the date's partition, or merge on a key. The {{ ds }} date in the command is what makes that possible, because the task always works on the same partition.

::::warn A task must know its date A task that uses datetime.now() instead of the run's logical date gives different results when it is rerun or backfilled. Pass the date in, and let Airflow supply it. ::::

Failure handling

Airflow gives several levels of response, which you should choose deliberately:

Mechanism Use for
Retries with delay Temporary network or database problems
Failure callback or email Notifying the owner of a failed task
Trigger rules Running a cleanup or alert task even when upstream fails
Sensors Waiting for a file or a partner's data to arrive, with a timeout
SLA alerts Warning when a task runs later than expected

A failure that should stop downstream work (a failed quality check) must block the tasks after it. A cleanup or alert task that must run regardless uses a trigger rule such as all_done.

Backfills

A backfill runs the DAG for past dates, usually after a bug fix. It is safe only if the tasks are idempotent. Run backfills in small date ranges, watch the load on the source and the warehouse, and check reconciliation after each batch.

Operating a DAG

  • Read the logs first. The failed task's log shows the real error; the DAG graph shows where the failure stopped the chain.
  • Clear and rerun one task after a fix, rather than rerunning the whole DAG, when the earlier tasks are already correct.
  • Keep DAGs small and readable. A DAG with two hundred tasks is hard to debug; split it by data domain.
  • Put secrets in a connection store or environment variables, never in the DAG file.
  • Test the DAG file with the Airflow import check and a dry run before deploying.
Interview cornerHow do you make an Airflow pipeline safe to rerun?

Make every task idempotent by working on the run's logical date and overwriting or merging its partition. Set bounded retries for transient errors, stop downstream tasks when a quality check fails, use catchup=False for new DAGs, and backfill in small batches with reconciliation after each one.

::::key What to remember - Airflow orchestrates tasks; it does not replace the tools that process the data. - A DAG is a set of tasks with dependencies; the schedule and retries are set per DAG or task. - Tasks must be idempotent and must use the run's date, not the current time. - Stop downstream work on failed checks; use trigger rules for cleanup and alerts. - Diagnose from the task log, fix, then clear and rerun the failed task. ::::

What dbt does

dbt (data build tool) turns SQL SELECT statements into managed tables and views, and adds the engineering practices software teams take for granted: dependencies, tests, documentation, version control and reviews. You write the transformation as SQL; dbt runs it in the right order, in your warehouse, and checks it.

Case studyA metric that changed without notice

An analyst changed how "active customer" is calculated inside a dashboard query. Three teams reported different numbers for a month, and nobody knew which was right. In dbt, the definition lives in one model, is tested and documented, and every downstream model references it, so a change is visible in review and in the lineage graph.

Models and ref()

A model is a SQL file that defines one table or view. The ref() function points to another model; dbt uses these references to build the dependency graph, so you never hard-code the order.

SQL
-- models/staging/stg_sales.sql
select
    row_id                      as sale_id,
    order_id,
    cast(order_date as date)    as order_date,
    customer_id,
    cast(sales as numeric(12, 2))  as sales,
    cast(profit as numeric(12, 2)) as profit
from {{ source('raw', 'superstore_sales') }}
SQL
-- models/marts/fct_monthly_sales.sql
select
    date_trunc('month', s.order_date) as month,
    c.region,
    sum(s.sales)  as sales,
    sum(s.profit) as profit
from {{ ref('stg_sales') }} as s
join {{ ref('stg_customers') }} as c using (customer_id)
group by 1, 2

source() names raw tables that dbt does not build. ref() names models that dbt builds. Both create the lineage links you will see in the documentation.

Layers in a dbt project

Layer Folder Rule
Staging models/staging One model per source table; renaming, typing and light cleaning only
Intermediate models/intermediate Reusable joins and logic that several marts need
Marts models/marts Business tables for reporting, with tests and descriptions

Keep business logic in marts and intermediate models, not in staging. A staging model that contains a revenue definition gets copied into every report that uses it.

Tests: generic and custom

Tests are queries that return the rows that break a rule. dbt runs them after each build; a failing test fails the build.

YAML
# models/marts/schema.yml
version: 2
models:
  - name: fct_monthly_sales
    description: "Sales and profit per month and region. One row per month and region."
    columns:
      - name: month
        tests: [not_null]
      - name: region
        tests:
          - not_null
          - accepted_values:
              values: ["North", "South", "East", "West"]
      - name: sales
        tests: [not_null]

Generic tests include unique, not_null, accepted_values and relationships (a foreign key exists in the parent table). A custom test is a SQL query that returns the failing rows, for a business rule:

SQL
-- tests/assert_sales_not_negative.sql
-- The test passes when this query returns no rows
select sale_id, sales
from {{ ref('stg_sales') }}
where sales < 0

::::tip Test the grain, not only the columns The most useful test on a fact table checks its grain: that one combination of keys appears once. Add a unique test on a surrogate key, or a test on the combination of key columns with dbt_utils.unique_combination_of_columns if you use that package. ::::

Documentation and lineage

Descriptions in the YAML become documentation. Running dbt docs generate and dbt docs serve produces a website with every model, column description, test and the lineage graph: which sources and models feed each model, and which dashboards depend on it. Lineage answers "if I change this column, what breaks?" before the change is made.

Running and reviewing changes

Terminal
dbt deps          # install packages
dbt build         # run the models and their tests in dependency order
dbt build --select fct_monthly_sales+   # the model and everything downstream of it
dbt test          # run tests only

A safe change follows the same path as software: a branch, a pull request that shows the changed SQL and the test results, a review, and a deployment that runs dbt build in a staging environment before production. Changes that alter a metric should include a comparison of old and new values for the last few months.

::::warn Incremental models need care Incremental models process only new rows for speed. A change to the logic does not rewrite old rows unless you force a full refresh. After changing an incremental model's logic, run a full refresh in staging and compare the totals with the previous version. ::::

Documentation habits that pay off

  • Write a one-sentence description for every mart and every key column.
  • Name the grain in the description ("one row per order line").
  • Record the owner of each model and the refresh schedule.
  • Keep the definition of each business metric in one model, and link to it from dashboards.
Interview cornerWhat does dbt add to plain SQL scripts?

Dependencies between models through ref(), a single build command that runs them in order, tests that run on every build, generated documentation and lineage, and a project structure that works with version control and code review. The SQL is the same; the discipline around it is what makes it maintainable.

Why Spark

Pandas works well while data fits in one machine's memory. When it does not, Spark splits the data into partitions and processes them in parallel on a cluster of machines. Its DataFrame API looks like pandas or SQL, but the work runs across many workers.

Case studyThe job that ran for six hours

A nightly job joined three years of transactions to a product table, then aggregated. It took six hours and sometimes failed with memory errors. The fix was not a bigger cluster: it was filtering early, broadcasting the small table, and removing an unnecessary shuffle. The job then ran in twelve minutes.

The architecture

Component Role
Driver Plans the work, holds the program, coordinates the executors
Executors Worker processes that run tasks on partitions and hold cached data
Partition A chunk of the data processed as one task
Cluster manager Allocates machines (YARN, Kubernetes, or the managed platform's own)

Lazy evaluation

Spark separates transformations (filter, select, join, groupBy) from actions (count, show, write). Transformations only build a plan. Nothing runs until an action asks for a result. Spark can then optimise the whole plan, combining steps and skipping work that is not needed.

Python
# Illustrative PySpark (not run: needs a Spark installation). Shows the pattern.
from pyspark.sql import SparkSession, functions as F

spark = SparkSession.builder.appName("sales_summary").getOrCreate()

sales = spark.read.option("header", True).option("inferSchema", True).csv("superstore_sales.csv")
products = spark.read.option("header", True).csv("products.csv")

summary = (
    sales
    .filter(F.col("order_date") >= "2024-01-01")          # transformation: filter early
    .join(F.broadcast(products), "product_id")            # broadcast the small table
    .groupBy("category", F.date_trunc("month", "order_date").alias("month"))
    .agg(F.sum("sales").alias("sales"), F.sum("profit").alias("profit"))
)

summary.explain()                                          # show the plan, not yet executed
summary.write.mode("overwrite").parquet("gold/monthly_category_sales")   # action: runs the job

explain() prints the plan Spark will run. write is the action that starts the work. Read the plan before you tune anything.

Shuffles: the expensive step

A shuffle moves data between executors so that rows with the same key end up together. Joins on non-broadcast tables and groupBy both shuffle. Shuffles write to disk and send data over the network, which is usually the slowest part of a job.

Operation Shuffle? Cheaper alternative
Filter, select, map No –
groupBy with aggregation Yes, but Spark pre-aggregates first Keep aggregations simple
Join with a large table Yes, both sides Partition both tables on the join key in advance
Join with a small table Avoidable broadcast(small_table)
Repeated sorting for each step Often Sort once, or avoid sorting

::::tip Broadcast the small table A join with a table that fits in memory can send a copy to every executor, so the big table never has to shuffle. Use F.broadcast() on the small side. Spark also does this automatically below a size threshold, but explicit hints make the intent clear. ::::

Partitions: how many and how big

  • Too few partitions leave executors idle; too many add scheduling overhead and tiny files.
  • A common starting point is a few partitions per core, and partitions of roughly 100 to 200 MB.
  • repartition(n) changes the number of partitions with a shuffle; coalesce(n) reduces it without one.

Data skew

Skew happens when one key holds most of the rows (for example, one customer id with a million orders). The task for that key runs far longer than the others, and the job waits for it. Diagnose skew in the Spark UI: one task takes much longer than its siblings. Fixes include filtering that key separately, salting the key, or aggregating in two stages.

Small files

Writing many tiny files slows every later read, because each file has overhead. Compact them with coalesce or the platform's compaction feature before writing the output for downstream use.

Caching

cache() or persist() keeps a DataFrame in memory when you use it more than once. Cache after expensive steps that feed several outputs, and unpersist when you finish. Caching everything wastes memory and can slow the job.

Streaming with Apache Kafka: Topics, Partitions, Consumers and Delivery Guarantees

Understand event streaming with Apache Kafka. Learn topics, partitions, offsets, consumer groups and retention, the three delivery guarantees (at most once, at least once, exactly once effect), and how to build a consumer that deduplicates and commits offsets safely.

● Gap-fill lesson✦ 2026Advanced⏱ 120 min
By the end of this lesson you can
  • Explain topics, partitions, offsets and consumer groups
  • Choose a delivery guarantee and design the consumer to match
  • Make a consumer idempotent with deduplication on event IDs

What Kafka is

Apache Kafka is a system for recording and distributing streams of events: a click, a payment, a sensor reading, an order status change. Producers write events to a topic; consumers read them. Kafka keeps the events for a set time, so consumers can read at their own pace, replay history, and join the stream later.

Case studyA payment that was counted twice

A payments service publishes "payment captured" events. A consumer that updates the ledger crashed after writing to the ledger but before recording its progress. On restart it re-read the event and counted the payment twice. The fix was not to avoid crashes; it was to make the consumer's write idempotent, so that a repeated event changes nothing.

Topics, partitions and offsets

A topic is a named stream. Each topic is split into partitions: ordered, append-only logs. Events with the same key always go to the same partition, so their order is kept for that key. Each event in a partition has an offset, a sequence number that a consumer uses to say where it has read up to.

Topic: orders
  Partition 0:  [offset 0] [offset 1] [offset 2] ...   keys A, C, A
  Partition 1:  [offset 0] [offset 1] ...              keys B, B

Partitions give parallelism: more partitions let more consumers read at once. Order is guaranteed only within a partition, which is why the key matters.

Consumer groups

A consumer group is a set of consumers that share a topic's partitions, so each partition is read by one member of the group at a time. Adding consumers to the group spreads the load. A second, separate group reads the same topic independently, which is how one stream feeds several systems (the warehouse, a fraud check, a dashboard).

Retention

Kafka keeps events for a configured time or size, whether or not consumers have read them. Retention makes replay possible: a new consumer can start from the beginning, or a consumer can rewind after a bug fix. It is not a permanent archive; long-term storage belongs in the lake.

Delivery guarantees

Guarantee Meaning When it happens Consequence
At most once An event may be lost but is never processed twice Offsets committed before processing Loss on failure
At least once An event is never lost but may be processed twice Offsets committed after processing Duplicates on failure
Exactly once (effect) The result is as if each event were processed once Idempotent processing, or transactions Requires design or transactional features

Most systems run at least once and make the processing idempotent. That is simpler and more robust than trying to make delivery itself exactly once.

An idempotent consumer

The consumer below is written as a pattern, not a finished program. It records each event's ID in the same transaction as the business write, so a repeated event is recognised and skipped.

Python
# Illustrative pattern (not run: needs a Kafka client and a database).
# Shows the logic that makes at-least-once delivery safe.

def handle(event, db):
    with db.transaction():                              # one transaction for both writes
        if db.exists("processed_events", event["event_id"]):
            return "skipped (already processed)"        # a duplicate: do nothing
        db.execute(
            "INSERT INTO ledger (order_id, amount) VALUES (%s, %s)",
            (event["order_id"], event["amount"]),
        )
        db.execute("INSERT INTO processed_events (event_id) VALUES (%s)", (event["event_id"],))
    return "processed"

# Offsets are committed only after handle() returns, so a crash causes a re-read,
# and the duplicate is skipped by the check above.

The key is that the business write and the record of processing succeed or fail together. If the record is written but the offset is not committed, the event is read again and skipped. If neither is written, the event is processed on the retry.

::::warn Commit offsets after the work, not before Committing the offset before processing turns a crash into a lost event. Commit after the work is safely stored, and make the work idempotent so that the repeat is harmless. ::::

Batch and streaming together

Kafka rarely replaces the warehouse. A common design lands the stream in the lake as files (for example, hourly Parquet partitions), and the batch pipelines of the earlier lessons process those files into reporting tables. Stream processing (Kafka Streams, Flink, Spark Structured Streaming) is used when the result must be updated within seconds, such as a fraud alert or a live stock count.

Need Choose
Reports refreshed daily Batch from files or tables
Reports refreshed hourly Micro-batch from landed files
Alerts within seconds Stream processing on Kafka
Feeding several systems from one source Kafka topic with several consumer groups

Operational checks

  • Consumer lag (how far behind the newest offset each group is) is the first health metric to watch.
  • Track the number of duplicates skipped; a rising number signals retries or producer problems.
  • Plan partition counts ahead, because increasing them later changes which partition each key goes to.
  • Protect topics with access control; events often contain personal data.
Interview cornerHow do you guarantee that a streaming consumer does not double-count?

Assume at-least-once delivery, because that is what most systems provide. Make each write idempotent by recording the event ID in the same transaction as the business write, skip events already recorded, and commit offsets only after the work is stored. Monitor consumer lag and the rate of skipped duplicates.

::::key What to remember - A topic is split into ordered partitions; order is guaranteed only within a partition, per key. - Consumer groups share the work and let several systems read the same topic independently. - Retention enables replay; it is not a permanent archive. - Design for at-least-once delivery and make processing idempotent. - Commit offsets after the work is stored, not before. ::::

Data Quality Dimensions, Observability, Catalogues, Lineage and Classification

Quality as measurable rules

"The data is good" means nothing until it is defined. Data quality is measured along dimensions, and each dimension becomes a rule that a query can test.

Dimension Question Example rule
Completeness Are required values present? customer_id is never null
Validity Do values follow the allowed format or range? discount between 0 and 1
Uniqueness Does each entity appear once? row_id is unique
Consistency Do related values agree? every customer_id in sales exists in customers
Timeliness Is the data recent enough? the newest order is at most one day old
Accuracy Does the data match the real world or a trusted source? daily totals match the finance ledger

Accuracy is the hardest dimension, because it needs a trusted reference. The others can be checked from the data itself.

Case studyThe report that was complete and wrong

A dashboard showed no missing values and no duplicates, and still reported 3% less revenue than finance. The rule set had no accuracy check. A reconciliation against the ledger found that one region's file had been loaded with an old exchange rate. Completeness and validity were fine; accuracy was not measured.

A quality check suite

Each check is a query that counts failing rows. Zero means pass. Store every result, so that trends are visible and a single failure can be investigated.

Python
import pandas as pd
import duckdb

con = duckdb.connect()
sales = pd.read_csv("superstore_sales.csv", parse_dates=["order_date"])
customers = pd.read_csv("customers.csv")
con.register("sales", sales)
con.register("customers", customers)

checks = {
    "completeness: customer_id is null":
        "SELECT COUNT(*) FROM sales WHERE customer_id IS NULL",
    "uniqueness: duplicate row_id":
        "SELECT COUNT(*) - COUNT(DISTINCT row_id) FROM sales",
    "validity: discount outside 0..1":
        "SELECT COUNT(*) FROM sales WHERE discount < 0 OR discount > 1",
    "validity: non-positive quantity":
        "SELECT COUNT(*) FROM sales WHERE quantity <= 0",
    "consistency: sales customer not in customers":
        "SELECT COUNT(*) FROM sales s LEFT JOIN customers c USING (customer_id) WHERE c.customer_id IS NULL",
}

results = []
for name, sql in checks.items():
    failing = con.execute(sql).fetchone()[0]
    results.append({"check": name, "failing_rows": failing, "status": "PASS" if failing == 0 else "FAIL"})

report = pd.DataFrame(results)
print(report.to_string(index=False))
Output
                                       check  failing_rows status
           completeness: customer_id is null             0   PASS
                uniqueness: duplicate row_id             0   PASS
             validity: discount outside 0..1             0   PASS
             validity: non-positive quantity             0   PASS
consistency: sales customer not in customers             0   PASS

The consistency check is the one that most often fails in practice. A sales row whose customer was deleted from the customer table disappears from a join and quietly understates totals.

::::tip Make the failure useful A check that says "FAIL" is not enough. Also store the failing rows (or a sample), the check name, the date and the threshold. Then the person on call can see what broke without rerunning the job. ::::

Thresholds and severity

Not every failure stops the pipeline. Decide severity in advance:

Severity Example Action
Blocking Null primary key, duplicate keys Stop the pipeline; do not publish
Warning 0.5% of discounts out of range Publish with a flag; alert the owner
Informational Row count up 12% week on week Record for trend review

Thresholds should come from the business. A 0.5% tolerance may be acceptable for marketing data and unacceptable for invoices.

Observability: knowing when something changes

Quality rules check the data you expect. Observability watches for the things you did not expect. Three signals cover most cases:

  1. Freshness. When did the newest record arrive? Alert if it is older than the agreed limit.
  2. Volume. How many rows arrived? Alert on sharp drops or spikes against a recent average.
  3. Schema. Did a column appear, disappear or change type? Alert before the change breaks a downstream model.
Python
import pandas as pd

history = pd.Series([1000, 1040, 980, 1010, 1025, 990, 1005])   # daily row counts, last week
today = 430
mean, std = history.mean(), history.std()
z = (today - mean) / std
print(f"today={today}, mean={mean:.0f}, z={z:.1f}")
print("ALERT: volume drop" if z < -3 else "volume within normal range")
Output
today=430, mean=1007, z=-28.3
ALERT: volume drop

A simple statistical rule such as "more than three standard deviations from the recent mean" catches most real incidents without tuning. Use a seasonal baseline for data with weekly patterns.

Catalogues, lineage and classification

A data catalogue is the inventory of datasets: what each one contains, who owns it, how fresh it is, and how to get access. A catalogue entry needs a description, an owner, a refresh schedule and a link to its quality results.

Lineage records where a dataset came from and what depends on it (see the dbt lesson for model-level lineage). It answers two questions: "why is this number wrong?" (trace upstream) and "who will be affected if I change this?" (trace downstream).

Classification labels columns by sensitivity: public, internal, confidential, personal. Classification drives access rules and masking. Classify at ingestion, store the label in the catalogue, and apply the masking rule in the layer that consumers read.

Column Classification Rule
order_id Internal Available to analysts
customer_name Personal Masked in silver and gold, restricted in bronze
sales Internal Available to analysts and finance
card number Personal, high risk Never loaded in raw form (see the ETL lesson)

Combine rules and signals: completeness and consistency checks on the source, freshness and volume monitoring on each load, reconciliation with a trusted total where one exists, and lineage to find the upstream table if something drifts. Alert the owner when a check fails, and show a quality status next to the dashboard.

The cloud service models

The cloud rents computing as services. The three main models differ in how much the provider manages for you.

Model You manage Provider manages Data example
IaaS (infrastructure) Operating system, runtime, data, applications Physical machines, network, storage hardware A virtual machine you install Airflow on
PaaS (platform) Data, code and configuration Servers, scaling, patching, runtime A managed warehouse or a managed Spark service
SaaS (software) Data and users The whole application A BI tool in the browser, a CRM

The more managed the service, the less you operate and the more you pay per unit of work. A team with few engineers usually chooses managed platforms for data, and keeps custom infrastructure for the parts that are truly special.

Case studyBuild or buy the warehouse

A five-person team considers installing a database on virtual machines. It would need patching, backups, scaling and on-call cover. A managed warehouse removes that work at a higher price per query. The decision is about where the team's time is best spent, not which option is technically superior.

Regions, availability and residency

A region is a geographic location with one or more data centres. An availability zone is an isolated data centre within a region. Choose regions for three reasons: latency to users, data residency law (for personal data, some countries require storage within their borders), and the availability of the services you need, because not every service exists in every region.

Keep the data platform in one region where possible, and replicate deliberately for disaster recovery. Cross-region copies cost money and add latency.

Identity and access

Cloud accounts use identities (users, groups, service accounts) and roles or policies that grant permissions. Four principles keep a data platform safe:

  1. Least privilege. Grant the smallest set of permissions a job needs.
  2. Service accounts for pipelines. A pipeline runs under its own identity, not a person's login.
  3. No long-lived keys in code. Use the platform's identity mechanism or a secrets manager.
  4. Audit. Every access and change to sensitive data is logged and reviewed.

docker run --rm -v "$PWD/data:/data" sales-summary:1.0 --input /data/daily_sales.csv --output /data/summary.csv

Key ideas:

  • Layer order matters. Put the things that change least (dependencies) first, so rebuilds are fast.
  • Pin versions in requirements.txt so that a rebuild next month does not change behaviour.
  • Do not copy secrets into the image. Pass them at run time as environment variables or from a secrets store.
  • Mount data rather than baking it in. The same image can then process today's file or last month's.

::::warn Images are not secret vaults Anything written into an image layer can be read by anyone who can pull the image, even if a later layer deletes it. Keep credentials out of the Dockerfile and out of the build context. ::::

What Kubernetes adds

Kubernetes runs containers across a cluster of machines. You describe the desired state (for example, "run three copies of this worker, restart it if it crashes, give it 2 GB of memory"), and Kubernetes keeps reality matching that description.

Kubernetes object Purpose in data work
Pod One or more containers that run together
Deployment Keeps a long-running service (for example a streaming consumer) alive

ConfigMap and Secret Configuration and credentials, kept out of the image
Horizontal autoscaler Adds workers when a queue grows

kind: CronJob
metadata:
  name: nightly-sales-summary

  schedule: "0 2 * * *"            # 02:00 every day

CI/CD for data projects

Continuous integration (CI) runs the tests and checks on every change. Continuous deployment (CD) releases a tested version to an environment automatically or with an approval step. For data, the pipeline should also run the data tests, not only the code tests.

A sensible pipeline for a dbt or Python data project:

YAML
# Illustrative CI workflow (GitHub Actions style); adapt to your platform
name: data-ci
on:
  pull_request:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: {python-version: "3.12"}
      - run: pip install -r requirements.txt
      - run: python -m pytest tests/             # unit tests for transformation code
      - run: dbt build --target ci               # models and their data tests in a CI schema
  deploy-staging:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - run: dbt build --target staging

The dbt build --target ci step builds into a temporary schema, so the tests run on real data structures without touching production. Deploy to staging only after the tests pass, and promote to production with an approval.

::::tip Test data, not only code A passing unit test does not prove the table is right. Include data tests (uniqueness, not-null, reconciliation totals) in the CI run, and fail the pipeline when they fail. A change that breaks a metric should be caught before the merge. ::::

Release habits

  • Tag each release with a version number; record which version produced each output table.
  • Keep environments separate (CI, staging, production) with their own credentials.
  • Make deployments reversible: keep the previous image and the previous dbt state, so a rollback is one command.
  • Never deploy by editing production by hand; the pipeline is the only route.
Interview cornerHow would you ship a change to a data pipeline safely?

Work on a branch, run unit and data tests in CI against a temporary schema, compare the output metrics with the previous version, deploy to staging, then promote to production with an approval and a recorded version. Keep the previous version available so that a rollback is quick.

::::key What to remember - Containers package code and dependencies so that a pipeline runs the same everywhere. - Layer Dockerfiles for fast rebuilds, pin versions, and keep secrets out of images. - Kubernetes runs and scales containers; use it when the operational need justifies it. - CI runs unit and data tests on every change; CD promotes tested versions with approval. - Version every release and keep rollbacks simple. ::::

Architecture starts with requirements

A data architecture is a set of decisions about how data moves and where it is stored. The decisions follow from requirements, and most bad architectures come from choosing tools before stating what they must do. Before drawing any diagram, write the requirements in measurable terms:

Requirement Measurable form
Freshness Dashboard shows data no older than 6 hours
Scale 200 million events a month, growing 30% a year
Trust Revenue matches the ledger within 0.5% every month
Cost Platform under £8,000 per month in year one
Security Personal data visible only to the customer team
Availability Reports available 99.5% of working hours

These numbers decide the architecture. A 6-hour freshness target does not need streaming; a 30-second fraud alert does.

Case studyThe architecture that was too fast

A team designed a streaming platform for a sales dashboard that the executives checked once a week. The platform cost four times the budget and was harder to test. A requirements review found that a daily batch pipeline met every need. The lesson is that the fastest architecture is not automatically the right one.

System design basics for data

Data systems fail in the same ways as other distributed systems. Four ideas explain most of the design choices.

Bottlenecks. The slowest component sets the speed of the whole system. Find it by measuring each stage: the source's query capacity, the network, the warehouse's concurrency, the dashboard's query count. Improving anything other than the bottleneck does nothing.

Caching. Store the result of an expensive computation and reuse it. A reporting table that is rebuilt nightly is a cache of the detailed data. A cache is correct only when its refresh rule matches the freshness requirement, and stale caches are a classic source of wrong numbers.

Replication and backup. Copies protect against loss and let reads spread out. Backups protect against mistakes: a deleted table or a bad load. Replication alone copies the mistake; backups and time travel let you go back.

Failure modes. Ask what happens when each component fails: the source is down, the ingestion job crashes, the warehouse is slow, a schema changes upstream. A good design says, for each failure, whether data is delayed, lost, duplicated or served wrongly, and how the team will know.

Failure Possible effect Design response
Source unavailable Data delayed Retry; alert on freshness; show "last updated" on dashboards
Duplicate delivery Totals overstated Idempotent loads and deduplication
Schema change upstream Pipeline breaks or silently mis-reads Schema checks; contracts with the source team
Warehouse overloaded Dashboards slow Serve summaries; limit concurrency
Bad load publishes Wrong numbers visible Quality gate before publish; rollback

A design walk-through: a retail sales platform

Requirements. Dashboards refresh by 07:00 with yesterday's sales (batch is enough). Revenue must reconcile with the ledger monthly. Personal customer data visible only to the customer team. Budget modest.

Design. 1. Sources: the point-of-sale system (nightly file export) and the online store (API, paginated). 2. Ingestion: a nightly batch job with a watermark and a safety window (see the ingestion lesson). 3. Storage: bronze, silver and gold layers (medallion, see the storage lesson), in one lakehouse. 4. Transformation: SQL models with tests, run after ingestion, with a quality gate before gold. 5. Serving: gold tables for dashboards; the customer team reads silver with masking applied. 6. Governance: catalogue entry per table with owner and freshness; personal fields classified and masked; monthly reconciliation to the ledger. 7. Failure responses: a missing file blocks the run and alerts the owner; a failed gate keeps yesterday's gold visible with a "data delayed" banner.

What was rejected and why. Streaming: not needed for daily reports and costly to operate. A second copy of the warehouse per team: duplicates cost and drifts; one lakehouse with access control is simpler.

Why the terminal matters for data work

Most data platforms run on Linux servers, and the fastest way to answer "is the pipeline running?" or "what went wrong last night?" is the command line. Command Purpose Example

Reading and searching files

Terminal
head -n 5 daily_sales.csv          # first five lines: check the header and format

Pipes and redirection

A pipe (|) sends the output of one command into another. Redirection (> and >>) sends output to a file. Together they answer operational questions in one line.

Terminal
# How many errors happened each hour in last night's log?
grep "ERROR" pipeline.log | cut -c1-13 | sort | uniq -c

# Save today's summary of rows per file, overwriting the old file
wc -l /data/landing/*.csv > row_counts.txt

# Append a timestamp line to a run history log
echo "$(date -Iseconds) load finished" >> run_history.log
Symbol Meaning
\| Pass the output to the next command
> Write the output to a file, replacing it
>> Append the output to a file
2>&1 Send error messages to the same place as normal output

::::tip Use >> for logs, > for results Overwriting a log with > by mistake erases the history of every earlier run. Use >> for logs that must be kept, and > only for output you intend to replace. ::::

Processes

A process is a running program. Check what is running and stop what is stuck:

Command Purpose
ps aux \| grep python Show Python processes and their owners
top or htop Live view of processes, CPU and memory use
kill PID Ask a process to stop (PID is the process number)
kill -9 PID Force a process to stop; use only when kill fails

Stop a process gently first. A forced stop can leave a file half-written, which is why an idempotent job (see the reliability lesson) is safer to restart than one that appends.

Permissions

Every file has an owner, a group and permissions for read (r), write (w) and execute (x). ls -l shows them:

-rw-r-----  1 analyst  finance  4096 Nov 11 06:00 summary.csv

This file is readable and writable by analyst, readable by the finance group, and hidden from everyone else. The commands that change permissions are chmod (mode), chown (owner) and chgrp (group).

Need Command Example
Let the team read a report chmod g+r chmod g+r summary.csv
Make a script runnable chmod +x chmod +x load.sh
Give a file to another owner chown (needs admin rights) sudo chown etl:etl summary.csv

Grant the least permission that works. Do not set everything to world-readable to fix one error; find the group that needs access and add the file to it.

::::warn Read before you delete rm -rf removes files without asking and without a recycle bin. Before deleting, list the matches with ls or find ... -print and check the paths. Never run a delete command with a variable that might be empty. ::::

A checklist for a server incident

  1. Confirm the time and the job: date, then the job's log with tail -n 100.
  2. Search for the first error: grep -n -m 1 "ERROR".
  3. Check resources: df -h (disk) and top (CPU and memory).
  4. Check the input: ls -lh and head on the expected file.
  5. Check the process: ps aux | grep <job>.
  6. Fix, rerun, and write a line in the run history with the cause.

Production troubleshooting: the order matters

When a live system fails, people often start by looking for the cause. The better order is to limit the damage first, then find the cause, then fix it properly.

Step Action Why this order
1. Confirm the impact Who is affected, and since when Decides how urgent the response is
2. Mitigate Rerun, roll back, switch to a safe source, or disable the feature Stops harm while the cause is unknown
3. Check recent changes Deployments, schema changes, new data sources, config changes Most failures follow a change
4. Check logs and freshness The first error, upstream freshness, row counts Locates the failing component
5. Reproduce Run the failing step on a copy or on a small input Confirms the cause before a fix
6. Fix the root cause The smallest change that removes the cause Prevents recurrence
7. Verify The original symptom is gone, and the checks pass Proves the fix
8. Prevent Add a test, an alert or a schema check Makes the next occurrence visible early
Case studyA column that was renamed upstream

A dashboard showed blank revenue for one region. Step 1 confirmed one region; step 2 switched the dashboard to the previous day's gold table; step 3 found that the source team had renamed a column the day before; step 4 showed the load succeeded with nulls in that column; step 5 reproduced it on a sample; step 6 mapped the new name; step 7 verified the numbers against the ledger; step 8 added a schema-change alert. Each step was short, and the sequence was the reason the incident ended quickly.

Troubleshooting an AI application

AI applications fail in new ways, so add these checks to the sequence:

  • Retrieval. Was the right document retrieved? Look at the retrieved chunks for the failing question.
  • Model input. Did the prompt contain what was expected (the right context, no leaked secrets, the right version)?
  • Tools. Did each tool return a valid result? A tool error often looks like a model error.
  • Version changes. Did the prompt, the model or the index change? Compare the regression suite with the last run.
  • Cost and latency. A sudden rise often means a loop or a larger context than intended.

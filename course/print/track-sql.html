What is a database?

A database is an organised collection of data stored so that it can be found, updated and analysed efficiently and safely by many people at the same time. A DBMS (database management system) is the software that manages it. Your bank balance, every Swiggy order, every Aadhaar-linked record and every hospital appointment lives in a database.

The vocabulary

Properties of SQL

  1. Declarative: you say what you want, not how to get it. The database's query optimiser decides the fastest way (which index, which join order).
  2. Set-based: statements work on whole sets of rows at once, not one row at a time like a loop.
  3. Not case-sensitive for keywords: select, SELECT and Select are the same. By convention, keywords are written in UPPERCASE. In SQL Server, text comparisons are usually case-insensitive too (default collation).
  4. Whitespace does not matter: you can split a query over many lines; indent it for readability.
  5. Statements end with a semicolon ; (optional in SQL Server for most statements, but a good habit).
  6. Standard, with dialects: the core is an ANSI/ISO standard; each product adds its own functions (T-SQL, PL/pgSQL, MySQL).

The families of SQL statements

Family Full name What it does Example
DDL Data Definition Language Creates and changes the structure: databases, tables, columns CREATE TABLE customers (...)
DML Data Manipulation Language Adds, changes and removes rows INSERT INTO customers VALUES (...)
DQL Data Query Language Reads data SELECT * FROM customers
DCL Data Control Language Gives and removes permissions GRANT SELECT ON customers TO analyst
TCL Transaction Control Language Groups changes so they succeed or fail together BEGIN TRAN … COMMIT

Many books put SELECT inside DML; others separate it as DQL. Both are fine in interviews if you explain them.

Interview cornerQuestions you may be asked

Q: What is the difference between DBMS and RDBMS? A DBMS manages data in any form; an RDBMS stores data in tables with relationships defined by keys, enforces integrity with constraints and uses SQL. Examples: SQL Server, PostgreSQL, MySQL, Oracle.

Q: Explain DDL, DML, DCL and TCL with examples. DDL changes structure (CREATE, ALTER, DROP, TRUNCATE); DML changes rows (INSERT, UPDATE, DELETE); DCL manages permissions (GRANT, REVOKE); TCL manages transactions (COMMIT, ROLLBACK, SAVE TRANSACTION). SELECT is sometimes called DQL.

Q: Why would a company keep data in SQL Server instead of Excel files? Concurrency, scale, data integrity (constraints, transactions), security and auditing, backup and recovery, and a single source of truth for reports and applications.

Why design matters

A database that is designed badly is slow, wastes space and, worst of all, lets data contradict itself. Imagine the customer's city stored in every order row: if the customer moves, you must update thousands of rows, and missing one creates two different "truths". Good design stores each fact once and connects tables with keys.

Entity–Relationship (ER) diagrams

An ER diagram is a picture of the data model before any table is created.

DefinitionBuilding blocks

Entity: a real-world thing you store data about: Customer, Order, Product, Employee. Becomes a table. Attribute: a property of an entity: name, city, price. Becomes a column. Relationship: how entities are associated: a Customer places Orders. Implemented with foreign keys. Cardinality: how many of one entity relate to another: one-to-one, one-to-many, many-to-many. Participation (optionality): whether the relationship is mandatory (every order must have a customer) or optional (a customer may have zero orders).

Crow's-foot notation

The most common notation in industry draws symbols at the ends of each relationship line:

Reading example: Customer ||——o< Order means "each order belongs to exactly one customer; each customer places zero or many orders".

Types of relationships

One-to-one (1:1)

Each row in A matches at most one row in B. Example: Employee ↔ Employee_Bank_Details. Often used to split sensitive or rarely used columns into a separate, more protected table. Implemented with a foreign key that is also unique (often the same as the primary key).

One-to-many (1:N) — the most common

One row in A matches many rows in B; each B row matches one A row. Examples: Customer → Orders, Department → Employees, Category → Products. The foreign key goes on the "many" side (orders.customer_id).

Many-to-many (M:N)

Many rows in A match many in B: Students ↔ Courses, Orders ↔ Products, Actors ↔ Movies. Relational tables cannot store this directly, so we add a junction (bridge, associative) table that holds a pair of foreign keys, turning one M:N into two 1:N relationships.

Relationship Example Where the foreign key goes
1 : 1 Employee – Passport Either side, marked UNIQUE
1 : N Department – Employees On the N side (employees.dept_id)
M : N Students – Courses In a junction table enrolments(student_id, course_id)
Self (recursive) Employee – Manager In the same table: employees.manager_id → employees.emp_id

Keys

Keys are columns (or sets of columns) with special meaning. They are among the most frequently asked interview topics.

Example table employees(emp_id, email, pan_number, name, dept_id, phone), where emp_id, email and pan_number are each unique:

Key type Definition Example
Super key Any set of columns that uniquely identifies a row (may include extra columns) {emp_id}, {emp_id, name}, {email, dept_id}
Candidate key A minimal super key: remove any column and it stops being unique {emp_id}, {email}, {pan_number}
Primary key (PK) The candidate key chosen to identify rows. Unique, not NULL, one per table emp_id
Alternate key Candidate keys not chosen as primary; enforce them with UNIQUE email, pan_number
Composite key A key made of two or more columns (order_id, product_id) in order_items; (student_id, course_id) in enrolments
Foreign key (FK) A column that refers to a PK (or unique key) in another table employees.dept_id → departments.dept_id
Unique key A UNIQUE constraint: no duplicates, but (in SQL Server) one NULL is allowed phone
Surrogate key An artificial key with no business meaning, often an auto-number customer_key INT IDENTITY(1,1)
Natural key A key with business meaning PAN number, GSTIN, ISBN, email
TipSurrogate or natural?

Natural keys can change (people change email, products get recoded) and can be long. Most warehouses and Power BI models use surrogate integer keys for joins, and keep natural keys as alternate (unique) keys.

Referential integrity

A foreign key guarantees that every child row points to a parent that exists: you cannot insert an order for customer C9999 if that customer does not exist. What happens when a parent row is deleted or its key is updated is controlled by the FK's actions:

Action On DELETE of the parent Use when
NO ACTION (default) The delete is blocked if children exist Most business data
CASCADE Children are deleted too Order → order items
SET NULL Children's FK becomes NULL Employee → manager who leaves
SET DEFAULT Children get the column's default Rare
SQL
CREATE TABLE departments (
    dept_id   INT PRIMARY KEY,
    dept_name VARCHAR(50) NOT NULL UNIQUE
);
CREATE TABLE employees (
    emp_id     INT PRIMARY KEY,
    email      VARCHAR(100) NOT NULL UNIQUE,          -- alternate key
    name       VARCHAR(100) NOT NULL,
    dept_id    INT NOT NULL REFERENCES departments(dept_id),   -- foreign key
    manager_id INT NULL REFERENCES employees(emp_id)           -- self-referencing FK
);

Normalisation

Normalisation organises columns and tables to reduce redundancy and avoid anomalies:

  • Update anomaly: the same fact stored in many rows gets changed in some but not others.
  • Insert anomaly: you cannot add a fact without another fact (cannot add a new product until someone orders it).
  • Delete anomaly: deleting one fact removes another (deleting the only order of a product deletes the product's information).

First normal form (1NF)

  • Each cell holds one atomic value (no lists like "Chair, Table").
  • No repeating groups of columns (product1, product2, product3).
  • Each row is unique (a key exists).

The flat file is already in 1NF: one product per row, and every row has a unique row_id. The natural key would be (order_id, product_id), but 70 lines repeat the same product within the same order, which is exactly why real systems add a surrogate key such as row_id or item_id.

Second normal form (2NF)

1NF and every non-key column depends on the whole key, not part of it (this matters only with composite keys). With key (order_id, product_id):

  • quantity, discount, sales depend on both: they stay.
  • order_date, customer_id, ship_mode depend only on order_id → move to an orders table.
  • product_name, category depend only on product_id → move to a products table.

Third normal form (3NF)

2NF and no transitive dependency: non-key columns must depend only on the key, not on other non-key columns. In orders, customer_name, city and region depend on customer_id, not on order_id → move them to a customers table.

"Every non-key attribute must provide a fact about the key, the whole key, and nothing but the key." (Bill Kent)

How much repetition did normalisation remove? Count the distinct customers and products versus rows:

SQL
SELECT COUNT(*)                     AS order_lines,
       COUNT(DISTINCT order_id)     AS orders,
       COUNT(DISTINCT customer_id)  AS customers,
       COUNT(DISTINCT product_id)   AS products
FROM superstore;
Result
order_lines orders customers products
6323 3200 785 78
1 rows × 4 columns

The flat file stores customer details 6,323 times; the normalised design stores them once per customer (fewer than 800 rows).

Normal form Rule in plain words
1NF One value per cell; no repeating columns; a key exists
2NF No column depends on only part of a composite key
3NF No column depends on another non-key column
BCNF Every determinant is a candidate key (stricter 3NF)
4NF / 5NF Remove multi-valued and join dependencies (rare in practice)

Denormalisation and the star schema

Transactional systems (OLTP) are normalised for safe, fast writes. Analytical systems (OLAP, data warehouses, Power BI) are often denormalised into a star schema: one central fact table (sales events with numbers) surrounded by dimension tables (customer, product, date, region) to make reading and aggregating fast and simple. You will build one in the Power BI track (Lesson 3).

Summary

Key takeaways
  • ER diagrams show entities (tables), attributes (columns) and relationships with cardinality (1:1, 1:N, M:N).
  • The foreign key sits on the many side; M:N needs a junction table with a composite key.
  • Super key ⊇ candidate keys (minimal); one candidate becomes the primary key (unique, not NULL), the others are alternate keys (UNIQUE).
  • Composite keys combine columns; surrogate keys are artificial integers; natural keys carry business meaning.
  • Foreign keys enforce referential integrity; ON DELETE CASCADE / SET NULL / NO ACTION decide what happens to children.
  • Normalise to 3NF to remove redundancy and anomalies; denormalise into a star schema for analytics.
Quick quiz6 questions · tap an answer to check it

1. Students can enrol in many courses and courses have many students. How do you model this?

Answer: C. A junction table resolves M:N into two 1:N relationships.

2. In a 1:N relationship between departments and employees, where does the foreign key go?

Answer: B. The FK goes on the "many" side: employees.dept_id.

3. Which statement about a primary key is FALSE?

Answer: C. A table has one primary key, which may be composite.

4. email is unique in the employees table but emp_id was chosen as the primary key. What is email?

Answer: B. Unchosen candidate keys are alternate keys, enforced with UNIQUE.

5. In orders(order_id, customer_id, customer_city), customer_city depends on customer_id. Which normal form is violated?

Answer: C. A non-key column depending on another non-key column is a transitive dependency, violating 3NF.

6. What does ON DELETE CASCADE on order_items.order_id do?

Answer: A. CASCADE propagates the delete to child rows.

Interview cornerQuestions you may be asked

Q: Difference between primary key, unique key and foreign key? PK uniquely identifies rows, no NULLs, one per table. A unique key also prevents duplicates but allows a NULL (one in SQL Server) and a table can have many. A foreign key references a PK/unique key in another table to enforce relationships.

Q: What is a candidate key? A composite key? A candidate key is a minimal set of columns that uniquely identifies rows; one is chosen as the PK. A composite key uses two or more columns together, such as (order_id, product_id).

Q: What is normalisation and why denormalise? Normalisation removes redundancy and anomalies (1NF–3NF). Data warehouses denormalise into star schemas to make analytical queries simpler and faster.

Why data types matter

Every column has exactly one data type. The type decides what values are allowed, how much storage they use, how they sort and compare, and which functions work on them. A column of dates stored as text sorts "01-02-2026" before "31-01-2025" and cannot be used for date arithmetic, the same problem you met in Excel.

NULL: the missing value

NULL means unknown or missing. It is not zero and not an empty string. Any comparison with NULL returns UNKNOWN, not TRUE or FALSE. SQL uses three-valued logic:

Expression Result
NULL = NULL UNKNOWN
NULL <> 5 UNKNOWN
5 + NULL NULL
TRUE AND UNKNOWN UNKNOWN
FALSE AND UNKNOWN FALSE
TRUE OR UNKNOWN TRUE
NOT UNKNOWN UNKNOWN

WHERE keeps only rows where the condition is TRUE, so rows where it is UNKNOWN disappear silently. That is why you must test with IS NULL:

SQL
WITH t AS (
    SELECT 'A' AS item, 10 AS score UNION ALL
    SELECT 'B', NULL UNION ALL
    SELECT 'C', 30
)
SELECT
    (SELECT COUNT(*) FROM t WHERE score = NULL)   AS equals_null_rows,     -- always 0!
    (SELECT COUNT(*) FROM t WHERE score IS NULL)  AS is_null_rows,
    (SELECT COUNT(score) FROM t)                  AS count_score,          -- ignores NULL
    (SELECT COUNT(*) FROM t)                      AS count_star,
    (SELECT AVG(score * 1.0) FROM t)              AS avg_ignores_null,     -- (10+30)/2
    (SELECT AVG(COALESCE(score, 0) * 1.0) FROM t) AS avg_null_as_zero;     -- (10+0+30)/3

T-SQL lets you store a value in a variable for the length of a batch. Variable names start with @.

Identifiers: naming rules and conventions

Rules (SQL Server): - Start with a letter, _, @ (variables) or # (temporary tables). - Up to 128 characters; letters, digits, _, @, $, #. - Reserved words (ORDER, GROUP, USER) and names with spaces must be wrapped in [square brackets] (or "double quotes"): [Order Details], [order].

Conventions used in this handbook (pick one style and be consistent): - snake_case, lowercase table and column names: order_items, customer_id. - Plural table names (customers) or singular (customer): be consistent. - Primary key id or <table>_id; foreign keys named after the referenced key (customer_id). - Prefix views vw_, procedures usp_, indexes ix_. - Avoid spaces, special characters and reserved words, so you never need brackets.

Interview cornerQuestions you may be asked

Q: What is the difference between CHAR, VARCHAR and NVARCHAR? CHAR is fixed length (padded), VARCHAR is variable length non-Unicode, NVARCHAR is variable length Unicode (two bytes per character for most scripts).

Q: DECIMAL vs FLOAT? DECIMAL is exact (money, rates); FLOAT is approximate binary (scientific values) and can introduce rounding errors.

MERGE: insert or update in one statement (upsert)

Data pipelines often receive a file of changes: some rows are new, others update existing rows. MERGE handles both:

SQL
MERGE dbo.staff AS target
USING dbo.staff_updates AS src
      ON target.emp_id = src.emp_id
WHEN MATCHED THEN
     UPDATE SET target.salary = src.salary, target.dept_id = src.dept_id
WHEN NOT MATCHED BY TARGET THEN
     INSERT (emp_id, full_name, email, dept_id, salary)
     VALUES (src.emp_id, src.full_name, src.email, src.dept_id, src.salary)
WHEN NOT MATCHED BY SOURCE THEN
     UPDATE SET target.is_active = 0;          -- in staff but not in the file

Q: DELETE vs TRUNCATE vs DROP? DELETE (DML) removes chosen rows with WHERE, logs each row, fires triggers and keeps IDENTITY. TRUNCATE (DDL) removes all rows quickly, minimal logging, resets IDENTITY, no WHERE, not allowed when referenced by a FK. DROP removes the whole table and its definition.

Q: What are constraints and why use them instead of app validation? Rules enforced by the database (PK, FK, UNIQUE, NOT NULL, CHECK, DEFAULT). They protect data no matter which app, script or person writes to the table.

Q: How do you safely run an UPDATE on production? Run the WHERE as a SELECT first, wrap in BEGIN TRAN, check @@ROWCOUNT and the result, then COMMIT or ROLLBACK; have a backup.

The logical processing order

You write SELECT first, but SQL processes the clauses in a different order. This explains several common errors.

Consequences:

  • You cannot use a column alias in WHERE, because WHERE runs before SELECT: WHERE margin_pct > 10 fails. Repeat the expression, or use a subquery/CTE.
  • You can use an alias in ORDER BY, because it runs after SELECT.
  • WHERE cannot contain aggregate functions (WHERE SUM(sales) > 100); use HAVING (Lesson 7).
SQL
-- Fails: Invalid column name 'margin_pct'
SELECT order_id, 100.0 * profit / sales AS margin_pct
FROM superstore
WHERE margin_pct > 10;

-- Works: repeat the expression in WHERE, use the alias in ORDER BY
SELECT order_id, 100.0 * profit / sales AS margin_pct
FROM superstore
WHERE 100.0 * profit / sales > 10
ORDER BY margin_pct DESC;

Summary

Key takeaways
  • SELECT columns and expressions; name them with AS; avoid SELECT * in saved queries.
  • DISTINCT removes duplicate rows of the selected columns; TOP n with ORDER BY limits results.
  • Filter with =, <>, >, <, >=, <=, AND/OR/NOT (use brackets), IN, BETWEEN (inclusive), LIKE with % and _, and IS NULL.
  • For dates use half-open ranges: >= start AND < next_start.
  • ORDER BY sorts ascending by default; can use aliases.
  • Logical order: FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → TOP. That is why aliases fail in WHERE.

Write one query that returns, for each order year: the number of orders, the number of distinct customers, total sales rounded to the nearest lakh (100,000), the average days to ship, and a comma-separated list of the ship modes used.

SQL
WITH modes AS (                                   -- one row per year and ship mode
    SELECT DISTINCT YEAR(order_date) AS order_year, ship_mode FROM orders
),
mode_list AS (
    SELECT order_year, STRING_AGG(ship_mode, ', ') AS ship_modes FROM modes GROUP BY order_year
)
SELECT YEAR(o.order_date)                                   AS order_year,
       COUNT(DISTINCT o.order_id)                           AS orders,
       COUNT(DISTINCT o.customer_id)                        AS customers,
       ROUND(SUM(oi.sales), -5)                             AS sales_nearest_lakh,
       AVG(DATEDIFF(day, o.order_date, o.ship_date) * 1.0)  AS avg_days_to_ship,
       MAX(m.ship_modes)                                    AS ship_modes
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.order_id
JOIN mode_list   AS m  ON m.order_year = YEAR(o.order_date)
GROUP BY YEAR(o.order_date)
ORDER BY order_year;

Summary

Key takeaways
  • GROUP BY makes one row per group; every selected column must be grouped or aggregated.

Why joins?

In a normalised database (Lesson 2) customer details live in customers, products in products, and orders in orders and order_items. To answer "sales by customer segment and product category" you must join them back together on their keys. A join is SQL's version of XLOOKUP (Excel Lesson 7) and pandas merge().

How many rows will a join return?

Join Rows returned
INNER Sum over matches; a key matching m rows on the left and n on the right produces m × n rows
LEFT Every left row at least once (more if it matches several right rows)
RIGHT Every right row at least once
FULL Matches + unmatched left + unmatched right
CROSS Left rows × right rows

Common join mistakes

1. Row explosion (fan-out)

Joining two "many" tables on a shared key multiplies rows. If you join order_items to another table with several rows per order (for example a payments table with instalments), each item is repeated for each payment and SUM(sales) is inflated. Always ask: what is one row of each table, and is the key unique on one side? Check with COUNT(*) before and after the join, or aggregate each table to the same grain first (Lesson 10).

2. Ambiguous column names

SELECT order_id FROM orders JOIN order_items ON … fails: "Ambiguous column name 'order_id'". Prefix columns with the table alias (o.order_id). Do it for every column in multi-table queries.

3. Filtering an outer join in WHERE

A condition on the right table placed in WHERE removes the NULL rows and silently turns a LEFT JOIN into an INNER JOIN:

SQL
-- Intended: all students, with their SQL course if any
SELECT s.name, e.course
FROM students AS s
LEFT JOIN enrolments AS e ON e.student_id = s.student_id
WHERE e.course = 'SQL';            -- wrong: drops students without SQL
Result
name course
Asha SQL
1 rows × 2 columns
SQL
SELECT s.name, e.course
FROM students AS s
LEFT JOIN enrolments AS e
       ON e.student_id = s.student_id
      AND e.course = 'SQL'         -- right: condition in ON keeps every student
ORDER BY s.student_id;
Result
name course
Asha SQL
Ravi NULL
Meera NULL
Kabir NULL
4 rows × 2 columns

4. Joining on the wrong or non-unique key

Joining customers to orders on city instead of customer_id creates nonsense matches. Join on keys, and check the relationship (1:1, 1:N) you expect.

5. NULL keys never match

NULL = NULL is UNKNOWN, so rows with a NULL key never match in any join. Clean or default keys first if that matters.

TipJoin check-list
  1. What is the grain (one row = ?) of each table? 2. Which key connects them, and is it unique on one side? 3. Do I need unmatched rows (LEFT/FULL) or only matches (INNER)? 4. Did the row count change as expected? 5. Are filters on outer-joined tables in ON or WHERE on purpose?

Older join syntax you may see

SQL
-- Implicit join (comma join), pre-1992 style: works but avoid
SELECT o.order_id, c.customer_name
FROM orders o, customers c
WHERE o.customer_id = c.customer_id;

Forgetting the WHERE turns it into a CROSS JOIN. Use explicit JOIN … ON.

Summary

Key takeaways
  • INNER: only matching rows. LEFT: all left rows + matches (NULLs where none). RIGHT: the mirror. FULL: everything. CROSS: every combination. SELF: a table with itself (aliases).
  • Anti-join: LEFT JOIN … WHERE right.key IS NULL finds rows with no match.
  • Join from the most detailed table outward, on keys, with aliases on every column.
  • Watch for row explosion, ambiguous columns, and filters on the right table in WHERE (move them to ON).
  • Joins = XLOOKUP / Power Query Merge / pandas merge / Power BI relationships.

Interview cornerQuestions you may be asked

Q: Explain the different types of joins. INNER returns matches; LEFT/RIGHT keep all rows from one side with NULLs where unmatched; FULL keeps all rows from both; CROSS returns every combination; SELF joins a table to itself.

Q: Table A has 5 rows with id 1 repeated twice, B has 3 rows with id 1 repeated three times. How many rows does an inner join on id return (other ids unmatched)? 2 × 3 = 6 rows.

Q: How do you find records in one table but not another? LEFT JOIN … WHERE right.key IS NULL, NOT EXISTS, or EXCEPT (Lesson 9).

Q: What is the difference between putting a condition in ON vs WHERE for a LEFT JOIN? In ON it only limits which right rows match (all left rows stay); in WHERE it filters the final result and removes unmatched left rows.

Set Operators: UNION, UNION ALL, INTERSECT & EXCEPT

Stack and compare query results. Append data with UNION ALL, remove duplicates with UNION, find common rows with INTERSECT and differences with EXCEPT, follow the rules for compatible columns, and know when to use a set operator instead of a join.

  • Append results with UNION ALL and de-duplicate with UNION

Joins add columns; set operators add rows

Rules for set operators

  1. Both queries must return the same number of columns.
  2. Corresponding columns must have compatible data types (text with text, numbers with numbers).
  3. Column names come from the first query.
  4. Only one ORDER BY, at the very end, applies to the combined result.
  5. UNION, INTERSECT and EXCEPT remove duplicates; UNION ALL does not.

UNION ALL: append

UNION ALL stacks results exactly as they are, like Power Query's Append or pasting one table under another. It is the fastest set operator because it does not check for duplicates.

SQL

UNION ALL
SELECT 'Technology', COUNT(*), ROUND(SUM(sales), 0) FROM superstore WHERE category = 'Technology'
UNION ALL
SELECT 'Office Supplies', COUNT(*), ROUND(SUM(sales), 0) FROM superstore WHERE category = 'Office Supplies'
ORDER BY sales DESC;

TipUNION or UNION ALL?

Use UNION ALL unless you need duplicates removed. UNION has to sort or hash the whole result to find duplicates, which is slow on large data, and it can silently remove rows that are genuinely repeated (two identical order lines).

Reconciliation and data-quality checks

Set operators are perfect for comparing two versions of the same data, for example a source system extract and the warehouse table:

SQL
-- Rows in the source extract that are missing or different in the warehouse
SELECT order_id, order_date, customer_id, total FROM staging.orders_extract
EXCEPT
SELECT order_id, order_date, customer_id, total FROM dw.fact_orders;

-- And the reverse: rows in the warehouse not in the source
SELECT order_id, order_date, customer_id, total FROM dw.fact_orders
EXCEPT
SELECT order_id, order_date, customer_id, total FROM staging.orders_extract;

If both queries return no rows, the two tables match exactly. Because set operators compare whole rows, any difference in any column shows up. (Set operators treat two NULLs as equal, unlike = in a join.)

Summary

Key takeaways
  • Joins add columns; set operators add or compare rows.
  • Rules: same number of columns, compatible types, names from the first query, one ORDER BY at the end.
  • UNION ALL appends everything (fast); UNION removes duplicates.
  • INTERSECT returns rows in both results; EXCEPT returns rows in the first but not the second (order matters).
  • Use them for combining periods, retention/churn analysis and reconciling systems.

     kept AS (SELECT customer_id FROM c24
              INTERSECT
              SELECT customer_id FROM orders WHERE YEAR(order_date) = 2025)

       COUNT(DISTINCT c24.customer_id)  AS customers_2024,

FROM c24
JOIN customers AS c ON c.customer_id = c24.customer_id
LEFT JOIN kept ON kept.customer_id = c24.customer_id
GROUP BY c.region
ORDER BY retention_pct DESC;

(CTEs with WITH are explained in Lesson 13.)

Interview cornerQuestions you may be asked

Q: UNION vs UNION ALL? UNION removes duplicate rows (slower); UNION ALL keeps all rows (faster). Use UNION ALL unless de-duplication is required.

Q: JOIN vs UNION? JOIN combines columns from related tables on a key; UNION stacks rows from queries with the same column structure.

Q: How would you check that two tables contain exactly the same data? Run A EXCEPT B and B EXCEPT A; both must return zero rows (also compare row counts to catch duplicates).

What is a subquery?

A subquery (inner query, nested query) is a SELECT written inside another statement, in brackets. The outer query uses its result.

By what it returns Example Used with
Scalar (one value) (SELECT AVG(sales) FROM superstore) =, >, < … or as a column
Multi-row (one column, many rows) (SELECT customer_id FROM orders WHERE …) IN, NOT IN, ANY, ALL, EXISTS
Table (many columns and rows) (SELECT region, SUM(sales) … GROUP BY region) FROM as a derived table

SQL

EXISTS and NOT EXISTS

EXISTS (subquery) is TRUE if the subquery returns at least one row. It stops at the first match, and the columns it selects do not matter (SELECT 1 is conventional).

"Customers who bought at least one Copier":

SQL
SELECT COUNT(*) AS customers_who_bought_copiers
FROM customers AS c
WHERE EXISTS (SELECT 1
              FROM orders AS o
              JOIN order_items AS oi ON oi.order_id = o.order_id
              JOIN products AS p     ON p.product_id = oi.product_id
              WHERE o.customer_id = c.customer_id
                AND p.sub_category = 'Copiers');

customers_who_bought_copiers
343
1 rows × 1 columns

SQL
SELECT COUNT(*) AS customers_without_orders
FROM customers AS c
WHERE NOT EXISTS (SELECT 1 FROM orders AS o WHERE o.customer_id = c.customer_id);

Why NOT EXISTS is safer than NOT IN

SQL
WITH a AS (SELECT 1 AS id UNION ALL SELECT 2 UNION ALL SELECT 3),
     b AS (SELECT 2 AS id UNION ALL SELECT NULL)
SELECT
    (SELECT COUNT(*) FROM a WHERE id NOT IN (SELECT id FROM b))                         AS not_in_rows,
    (SELECT COUNT(*) FROM a WHERE NOT EXISTS (SELECT 1 FROM b WHERE b.id = a.id))       AS not_exists_rows;
Result
not_in_rows not_exists_rows
0 2
1 rows × 2 columns

NOT IN returns 0 rows because b contains a NULL: 3 NOT IN (2, NULL) means 3 <> 2 AND 3 <> NULL, which is UNKNOWN. NOT EXISTS correctly returns 2 rows (1 and 3). Prefer NOT EXISTS, or add WHERE id IS NOT NULL inside the NOT IN subquery.

Derived tables (inline views)

A subquery in FROM acts as a temporary table for the rest of the query. It must have an alias. Derived tables are the standard way to aggregate first, then filter, join or aggregate again.

"Average order value by segment" requires two levels: first total each order, then average the orders.

SQL
SELECT segment,
       COUNT(*)                   AS orders,
       ROUND(AVG(order_total), 0) AS avg_order_value
FROM (
    SELECT o.order_id, c.segment, SUM(oi.sales) AS order_total     -- level 1: one row per order
    FROM orders AS o
    JOIN customers AS c    ON c.customer_id = o.customer_id
    JOIN order_items AS oi ON oi.order_id   = o.order_id
    GROUP BY o.order_id, c.segment
) AS order_totals                                                    -- level 2: average of orders
GROUP BY segment
ORDER BY avg_order_value DESC;
Result
segment orders avg_order_value
Consumer 1554 63,451
Home Office 691 63,237
Corporate 955 61,899
3 rows × 3 columns

If you averaged oi.sales directly, you would get the average line value, not the average order value: a frequent interview trap.

NoteNested (ordinary) subqueries vs inline views

A subquery in WHERE that does not refer to the outer query is an ordinary (nested) subquery: it runs once. A subquery in FROM is an inline view (derived table). One that refers to the outer row is correlated. In class these were introduced as inline views and ordinary subqueries; the next step is the CTE (Lesson 13), which is a named, more readable inline view.

Choosing the right tool

Need Good options
Compare with an overall aggregate Scalar subquery, or window function
Filter by membership in another table IN, EXISTS, or JOIN
Rows with no match NOT EXISTS (safest), LEFT JOIN … IS NULL, EXCEPT
Compare with the row's own group Correlated subquery, or AVG() OVER (PARTITION BY …)
Aggregate in two steps Derived table or CTE
Reuse the same subquery several times CTE (Lesson 13)

Summary

Key takeaways
  • Subqueries are queries in brackets inside another query; they can return a value, a list or a table.
  • Scalar subqueries compare with or display a single value (e.g. the overall average).
  • IN, ANY, ALL work with multi-row subqueries; > ALL = greater than the max.
  • Correlated subqueries reference the outer row (e.g. above the employee's department average).
  • EXISTS / NOT EXISTS test for matching rows; prefer NOT EXISTS over NOT IN when NULLs are possible.
  • Derived tables (inline views) aggregate first, then filter/join; they need an alias.

Interview cornerQuestions you may be asked

Q: Difference between a correlated and a non-correlated subquery? A non-correlated subquery runs independently once; a correlated subquery references the outer query and is evaluated per outer row.

Q: EXISTS vs IN? IN compares a value with a list; EXISTS checks for the existence of matching rows and stops at the first one. EXISTS handles NULLs safely in the negative form (NOT EXISTS).

Q: Find employees who earn more than their department's average. Correlated subquery on department, or AVG(income) OVER (PARTITION BY department) in a CTE and filter.

Q: Subquery vs JOIN: which is faster? It depends; modern optimisers often produce the same plan. Joins are usually clearer for combining columns; EXISTS for existence tests; derived tables/CTEs for multi-step aggregation. Check the execution plan.

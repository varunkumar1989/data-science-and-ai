Excel and Power BI questions

Question Short answer
VLOOKUP vs XLOOKUP vs INDEX-MATCH? XLOOKUP looks left/right, has defaults and exact match by default; INDEX-MATCH works in older versions; VLOOKUP breaks when columns move
Pivot table vs Power Pivot? Power Pivot uses a data model with relationships and DAX measures across tables
Calculated column vs measure (DAX)? Columns are computed row by row and stored; measures are evaluated in filter context at query time
What does CALCULATE do? Evaluates an expression in a modified filter context
Star schema? Fact table of events joined to dimension tables; simpler, faster models
Import vs DirectQuery? Import copies data (fast, scheduled refresh); DirectQuery queries the source live (fresh, slower)
Row-level security? Roles with DAX filters so users see only their rows

Statistics and experiments

Be ready to explain: mean vs median, standard deviation, distributions, correlation vs causation, confidence intervals, p-values, Type I/II errors, sample size and A/B test pitfalls (peeking, SRM, novelty). See ML lessons 1–6 for model answers.

Case questions: a framework

  1. Clarify the metric and time frame. 2. Check data quality first. 3. Segment (where is the drop?). 4. Form hypotheses (internal vs external). 5. Validate with data. 6. Recommend action and how you would measure it.

Product-sense metrics: define a north-star metric, input metrics and guardrails (e.g. for a food-delivery app: weekly ordering customers; conversion, delivery time, order value; cancellations, complaints).

Behavioural: STAR

Situation (context) → Task (your goal) → Action (what you did, with tools) → Result (numbers, learning). Prepare 6 stories: a project you are proud of, a mistake you fixed, a conflict, a tight deadline, influencing without authority, learning a new tool fast.

Python and pandas (quick answers)

Question Answer
List vs tuple vs set vs dict? Mutable sequence / immutable record / unique unordered / key→value; sets and dicts give O(1) lookups
apply vs vectorisation? Vectorised column operations run in C and are much faster; avoid apply(axis=1) on large data
merge vs join vs concat? merge on columns, join on index, concat stacks
How to handle missing values? Understand why, then drop, impute (median, group-wise, model) or flag; impute inside CV
Generator vs list? Generators are lazy and memory-efficient, consumed once

Statistics and ML fundamentals

Question Model answer
Bias-variance trade-off? Simple models underfit (bias), complex models overfit (variance); choose complexity by validation error
L1 vs L2? L1 zeroes coefficients (selection); L2 shrinks smoothly; Elastic Net mixes
Why cross-validation? A single split is noisy; k-fold averages and supports tuning without touching the test set
Precision vs recall? Precision: flagged that are right; recall: positives caught; choose by error costs
ROC-AUC vs PR-AUC? PR-AUC is more informative for rare positives
Bagging vs boosting? Parallel averaging (variance) vs sequential error correction (bias)
How does gradient descent work? Iteratively step weights against the loss gradient with a learning rate
What is data leakage? Using information unavailable at prediction time; prevent with pipelines, time-based splits and feature cut-offs
p-value? Probability of data at least this extreme if H0 were true; not the probability H0 is true

ML system design: a template

Example: "Design a fraud detection system for UPI payments." Real-time decision under 100 ms; label = confirmed fraud (delayed, imbalanced); features: amount vs user history, device/location change, merchant risk, velocity, graph links; model: gradient boosting + rules + anomaly scores; evaluate PR-AUC and recall at alert capacity; serve with a feature store and low-latency API; monitor drift and attack patterns; human review queue; A/B test thresholds.

LLM, RAG and agent questions

Question Model answer
How do LLMs work? Transformers trained to predict the next token, then instruction-tuned and aligned with feedback
RAG vs fine-tuning? RAG for changing knowledge with citations; fine-tuning for behaviour/format
How to evaluate a RAG system? Retrieval hit rate/MRR + answer correctness, faithfulness, abstention on a labelled set
How to reduce hallucinations? Grounding, tools, "say I don't know", citations, validation, evaluation
What is an agent? An LLM in a loop choosing tool actions toward a goal, with memory and stopping conditions
What is MCP? Open protocol to connect assistants to tools/data via servers (tools, resources, prompts)
Prompt injection defence? Separate data from instructions, least-privilege tools, approvals, output checks
Cost control? Model routing, caching, batching, shorter context and outputs

Data Engineering and Analytics Interview Questions with Model Answers

Practise twelve core questions on ETL versus ELT, idempotency, batch and streaming, schemas, surrogate keys, late data, dbt tests, Airflow, Spark shuffles, warehouses versus lakehouses, pipeline testing and change data capture, each with a model answer and the reasoning an interviewer listens for.

● Gap-fill lesson✦ 2026Intermediate⏱ 120 min
By the end of this lesson you can
  • Answer core data engineering and analytics questions clearly and briefly
  • Give the trade-off behind each answer, not only the definition
  • Recognise follow-up questions that test depth

How interviewers use these questions

Interviewers rarely want a textbook definition. They listen for four things: whether you know the term, whether you can explain it simply, whether you know when it applies, and whether you know its trade-off. A good answer covers all four in under two minutes. The model answers below are written at that length.

The twelve questions

1. What is the difference between ETL and ELT? Model answer. ETL transforms data before loading it into the target; ELT loads raw data first and transforms it inside the warehouse. ELT suits cloud warehouses that have cheap, powerful compute, and it keeps raw data so models can be rebuilt. ETL is chosen when data must be masked or validated before it lands, for example personal data that must never reach the warehouse in raw form.

2. What is idempotency? Model answer. An operation is idempotent when running it twice has the same effect as running it once. Pipelines need this because retries and reruns are normal. A load that appends rows is not idempotent; a load that merges on a key, or overwrites a partition, is.

3. Batch versus streaming? Model answer. Batch processes accumulated data at intervals, such as nightly. Streaming processes each event as it arrives. Batch is simpler, cheaper and easier to test; streaming gives low latency at higher operational cost. Choose by how fresh the data must be and what it costs to be late.

4. Star versus snowflake schema? Model answer. Both have a central fact table and dimension tables. A star schema keeps each dimension flat, which makes queries simple and fast. A snowflake normalises dimensions into sub-tables, which saves a little storage and adds joins. Star schemas are usually preferred for reporting; snowflakes appear where dimensions are very large or shared.

5. What is a surrogate key and why use it? Model answer. A surrogate key is a system-generated identifier, such as an integer, that has no business meaning. It keeps the warehouse stable when source keys change, reduces join size, and is essential for slowly changing dimensions where one customer has several versions over time.

6. How do you handle late-arriving data? Model answer. First, decide the tolerance: how late can a record arrive and still count? Then reprocess the affected partitions or window rather than only appending new rows, use the event time rather than arrival time for aggregates, and report the restated numbers with a note. Monitor how often late data arrives so the window can be tuned.

7. What does a dbt test check? Model answer. dbt tests check assumptions about a model's data: that a column is unique, not null, that values belong to an accepted list, or that a relationship between tables holds. They run on every build, and a failing test stops the pipeline from publishing wrong data. Custom tests can check business rules, such as "revenue is never negative".

8. What is Airflow used for? Model answer. Airflow schedules and orchestrates workflows defined as directed acyclic graphs (DAGs). It runs tasks in dependency order, retries failures, records run history and alerts on errors. It does not process the data itself; it calls the tools that do.

9. Spark shuffles and partitions? Model answer. A shuffle is the redistribution of data across the cluster, typically for a join or a group-by, and it is expensive because data moves over the network. Partitions are the units of parallel work. Too few partitions leave machines idle; too many add overhead. Reducing shuffles, filtering early and choosing sensible partition counts are the usual fixes for slow jobs.

10. Warehouse versus lakehouse? Model answer. A warehouse stores structured tables with strong SQL performance and governance. A lakehouse keeps data in open file formats on cheap storage and adds table features such as transactions and schema management, so it can serve both analytics and machine learning. Many organisations use both: a lakehouse for raw and mixed data, and a warehouse or serving layer for reporting.

11. How do you test a data pipeline? Model answer. Test at four levels: unit tests for transformation functions on small inputs; schema tests on each table; data-quality tests such as row counts, nulls and reconciliation totals against the source; and an end-to-end run on sample data. Add a failure drill, where you break an input on purpose and confirm the alert fires.

12. What is CDC? Model answer. Change data capture reads a database's change log to capture inserts, updates and deletes as they happen, instead of re-reading whole tables. It keeps the warehouse close to real time at low load on the source. It needs database access for the log and careful handling of schema changes.

Business Scenario Interviews: Seven Problems and Answer Frameworks

Practise seven open-ended business scenarios, from a sales decline and rising churn to a slow dashboard, a failed pipeline, an incorrect AI assistant and a vague stakeholder request. Each has a structured answer framework: clarify, hypothesise, analyse, recommend and measure.

● Gap-fill lesson✦ 2026Intermediate⏱ 120 min
By the end of this lesson you can
  • Structure an open-ended business answer with a repeatable framework
  • Ask the clarifying questions that show judgement before analysing
  • Propose tests and measures, not only conclusions
  • Recognise when the right answer is "I need to clarify the requirement first"

What a scenario interview tests

Scenario questions have no single right answer. The interviewer is judging how you think: whether you clarify before you analyse, whether your hypotheses are specific enough to test, whether you choose the cheapest test that would change a decision, and whether you can recommend an action and say how you will know it worked.

The framework

Use the same five steps for every scenario, and say the step names aloud.

  1. Clarify. What exactly happened, over what period, for which segment, compared with what? Ask two or three questions before answering.
  2. Hypothesise. List three to five possible causes, ranked by how likely and how cheap they are to check.
  3. Analyse. For each hypothesis, name the data that would confirm or reject it, and the test or query you would run.
  4. Recommend. State the most likely cause and the action, with the trade-off.
  5. Measure. Name the metric that will show the action worked, and the timeframe.

Scenario 1: sales have declined by 20%

  • Clarify: Which products, regions and channels? Compared with last month, last year, or the plan? Did prices, stock or the sales team change?
  • Hypotheses: a data or reporting change; a seasonal effect; lost customers; lower traffic; a stock-out; a price change; a competitor move.
  • Analysis: split the decline by region, product, channel and customer type; compare new and repeat customers; check whether the drop comes from fewer orders or smaller orders; reconcile the total with the finance ledger.
  • Recommend: act on the largest confirmed driver only. If the data is wrong, the first action is to fix the data.
  • Measure: weekly sales in the affected segment against a comparison group.

Scenario 2: customer churn has increased

  • Clarify: How is churn defined (cancellation, or no order for 90 days)? Which customer groups? Since when?
  • Hypotheses: a price increase; a product issue; a support problem; a competitor offer; a cohort acquired through a weak channel.
  • Analysis: cohort retention by sign-up month and channel; the tenure at which customers leave; support tickets before churn; the share of churners who used a discount.
  • Recommend: a targeted retention offer for the group most at risk, with a control group to measure it.
  • Measure: retention of the treated group against the control after 60 to 90 days.

Scenario 3: a dashboard is slow

  • Clarify: How slow, for whom, and since when? Which filters? Is it the first load or each interaction?
  • Hypotheses: too much data in the model; inefficient measures; too many visuals; a slow data source; unlimited filters.
  • Analysis: check the query and refresh timings; count the rows loaded; find the measures that scan the most data.
  • Recommend: aggregate the fact table to the level the dashboard needs, simplify the most expensive measures, and reduce the visuals on the first page.
  • Measure: time to first render, p95, and user feedback.

Scenario 4: a data pipeline has failed

  • Clarify: Which job, which step, what error, since when, and what depends on it? Is it the first failure or a repeat?
  • Hypotheses: a source schema change; a late file; a permission change; a memory limit; a bad record; a changed API.
  • Analysis: read the logs at the failing step; compare row counts with the previous run; check upstream jobs and the source schema.
  • Recommend: restore service first (rerun the failed partition if the job is idempotent), then fix the cause and add a test that would have caught it.
  • Measure: time to detect and time to recover, and whether the same failure recurs.

Scenario 5: an AI assistant gives incorrect answers

  • Clarify: Which questions, how often, and how wrong? Did the assistant have the right documents? Was the answer checked by a person?
  • Hypotheses: retrieval missed the right document; the document is out of date; the prompt allows guessing; the model is wrong on a specific topic; a tool returned bad data.
  • Analysis: build a test set of the failing questions; check whether the right passage was retrieved; read the answers against the sources; check tool outputs.
  • Recommend: fix the cause that the test points to (retrieval, content, prompt or tool), and add the cases to the regression suite.
  • Measure: accuracy on the test set and the rate of wrong answers reported by users.

Scenario 6: an enterprise customer wants to automate a manual workflow

  • Clarify: What is the workflow today, how long does it take, how often, what goes wrong, and who approves each step?
  • Hypotheses: the workflow is fixed (a workflow tool suffices); it needs judgement at some steps (an agent with approval); the data is not ready.
  • Design: map the steps; mark each as deterministic, model-driven or needing a person; choose the simplest tool; define the approval points, the data access and the logs.
  • Recommend: a pilot on one part of the workflow with a clear success measure and a stop rule.
  • Measure: time per case, error rate, the share handled without a person, and cost per case.

Scenario 7: a stakeholder asks for a dashboard but cannot define the requirements

  • Clarify: What decision will this dashboard support? Who will use it, and how often? What would they do differently if it showed X?
  • Hypotheses: the stakeholder knows the problem but not the measures; they need an example before they can specify.
  • Approach: run a short discovery: interview two users, sketch three layouts on paper, and agree the first three questions the dashboard must answer.
  • Recommend: build a first version with the three agreed questions, show it, and collect changes.
  • Measure: whether the stakeholder uses it in a real meeting within a month.
Interview cornerThe strongest answer to a vague request

Say that you would not build anything yet. Explain the decision the work must support, propose a 30-minute discovery session, and describe the smallest version you would show within a week. Interviewers reward candidates who protect the team from building the wrong thing.

::::key What to remember - Clarify before analysing; two good questions show judgement. - Rank hypotheses by likelihood and by how cheap they are to test. - Recommend one action with its trade-off, and name the measure that proves it worked. - For a vague request, the first deliverable is a decision and a shared definition. ::::

Behavioural Interviews and STAR Answers

Prepare answers to seven common behavioural questions using the STAR method (Situation, Task, Action, Result). Learn to structure a two-minute story, show your own contribution, include a measurable result, and tell an honest story about a failure or a conflict.

● Gap-fill lesson✦ 2026Beginner⏱ 90 min
By the end of this lesson you can
  • Structure a behavioural answer using STAR
  • Describe your own actions clearly, without taking credit for the team's work
  • Include a result, with a number where possible
  • Talk honestly about a failed project and what changed afterwards

The STAR method

Behavioural questions ask "tell me about a time when..." The interviewer wants evidence of how you actually work. The STAR structure gives a clear story in about two minutes:

Part Length What to say
Situation 1–2 sentences Where you were, what the context was
Task 1 sentence What you were responsible for
Action 60–90 seconds What you did, step by step, using "I" for your own work
Result 20–30 seconds What changed, with a measure, and what you learned

Most weak answers spend too long on the situation and not enough on the action and result. Aim for the action to be the longest part.

Case studyThe same project, told two ways

A weak answer: "We had a messy spreadsheet and the team was struggling, so we worked on it and it got better." A STAR answer: "Our monthly churn report was built by hand and took two days, with errors found by finance each time. My task was to automate it without changing the numbers. I wrote a cleaning script with checks for each source, compared its output with the manual report for three months, and set up a scheduled run. The report now takes ten minutes and the variance to finance is under 0.5%." The second answer names the action and the measure.

Question 1: tell me about yourself

Use a 90-second version: your current role or study, two relevant skills with an example each, and why this role. End with a sentence connecting to the job. Do not recite your CV.

Question 2: explain a difficult project

Choose a project with real obstacles. Describe the constraint (data quality, a deadline, a changing requirement), the step you took to get past it, and what you would do differently. A project that was hard but went well is a good choice.

Question 3: describe a problem you solved

Pick a problem with a clear cause and a verifiable fix. Show how you diagnosed it: what you checked first, what the evidence showed, and why you chose the fix you did. Quantify the result where you can.

Question 4: explain a conflict with a stakeholder

Describe the disagreement fairly, including the other person's valid concern. Show how you found common ground: a shared definition, a small pilot or a data check. Avoid describing the other person as the problem; describe what you changed in how you worked together.

Question 5: describe a failed project

Be honest. Choose a real failure with a lesson. Explain what you expected, what went wrong, what you did when you noticed, and what you do differently now. Interviewers trust candidates who can name a mistake and show a changed habit.

Watch outDo not invent results

Never state a number you cannot support. If the result is qualitative, say so: "the team adopted it, and two colleagues now use the same check." If you do not know the impact, say how you would measure it. Interviewers often ask a follow-up about the number, and an invented figure falls apart.

Question 6: how do you prioritise work?

Describe a method you actually use: for example, ranking by business impact and effort, asking the requester what decision the work supports, and reviewing the list weekly. Give one example where you said no or postponed a request, and why.

Question 7: how do you explain technical concepts to non-technical stakeholders?

Show a technique: start with the decision, use one concrete example, avoid jargon or define it once, and check understanding by asking the person to restate the implication. Give an example where a chart or a single number replaced a long explanation.

Preparing your stories

Prepare five stories that each cover different themes (a success, a failure, a conflict, a difficult deadline, a learning moment). Each story can answer several questions. Write each in STAR form, time it, and practise until it fits in about two minutes without notes.

Story Useful for questions
Automated the monthly report 2, 3, 6
Disagreement over a metric definition 4, 7
A pipeline failure that taught a lesson 2, 5
A dashboard that went unused 5, 6, 7
A course or project you completed on your own 1, 3

::::tip Practise with a recording Record your answers on a phone. Check whether the action is the longest part, whether you say "I" for your own work, and whether the result has a number or a clear change. Re-record until each answer lands in two minutes. ::::

::::key What to remember - Use STAR: short situation and task, a detailed action, and a result with a measure. - Say "I" for what you did; say "we" for the team's work, and be clear about your share. - Never invent numbers; say how you would measure an unknown impact. - Prepare five stories that cover several questions each. ::::

Eight Capstone Project Briefs and the Portfolio Checklist

Choose one of eight portfolio-level capstone projects covering dashboards, churn prediction, an end-to-end data pipeline, an AI data analyst, an enterprise RAG assistant, an agent for business operations, an MCP business assistant and an industry-specific project. Each brief has requirements, deliverables and an evaluation rubric, and a checklist makes every project presentable to an employer.

● Gap-fill lesson✦ 2026Advanced⏱ 150 min
By the end of this lesson you can
  • Scope a portfolio project with clear requirements and deliverables
  • Choose a project that matches your target role
  • Prepare a project so that an employer can review it in ten minutes
  • Evaluate your own work against the rubric before you show it

How to use these briefs

Choose two projects, not eight: one that matches your target role closely, and one that shows a different skill. Each brief has the same parts: the problem, requirements, deliverables, the data to use, and the rubric the work will be judged against. Read the rubric first; it tells you what matters most.

Project 1: Business analytics dashboard

  • Problem: a regional sales manager needs to see revenue, margin and returns by region, category and month, and to spot where profit is falling.
  • Requirements: a clean star schema; at least 8 measures in one measure table; a page for trends, a page for drill-down, and a page of exceptions; a filter for date and region.
  • Deliverables: the report file, a 1-page guide for users, and a README explaining the data source and refresh.
  • Data: superstore_sales.csv.
  • Rubric: correctness of totals against a control (30%); clarity of the first page (25%); measures documented and tested (25%); usability on a phone or small screen (20%).

Project 2: Customer churn prediction

  • Problem: a telecom company wants to know which customers are likely to leave in the next month, so that a retention offer can be targeted.
  • Requirements: a defined churn label; a train and test split that respects time; a baseline model; one stronger model; evaluation with precision, recall and a business cost; an explanation of the top drivers.
  • Deliverables: a notebook, a short model card, and a one-page recommendation with the expected value of the offer.
  • Data: telecom_churn.csv.
  • Rubric: a sound split and leakage check (30%); evaluation that matches the business cost (30%); explanation in plain language (25%); reproducibility (15%).

Project 3: End-to-end data engineering pipeline

  • Problem: daily sales files arrive from several sources and must become a trusted reporting table.
  • Requirements: raw, cleaned and reporting layers (medallion layout); idempotent loads with a key; data-quality checks (nulls, duplicates, row counts, reconciliation); a scheduled run; logs and a failure alert.
  • Deliverables: code in a repository, a diagram of the layers, the test results, and a failure drill with notes.
  • Data: daily_sales.csv split into daily files, plus a second file with customer data.
  • Rubric: correctness and re-run safety (35%); tests and checks (25%); operations: schedule, logs, alerts (25%); documentation (15%).

Project 4: AI-powered data analyst

  • Problem: managers ask data questions in plain English and wait days for answers.
  • Requirements: natural-language questions turned into safe SQL against a read-only database; a row limit; the SQL shown with each answer; a test set of 30 questions with known answers; a refusal for anything outside the data.
  • Deliverables: the working assistant, the test set and its results, and a short note on errors found.
  • Data: superstore_sales.csv loaded into a database.
  • Rubric: accuracy on the test set (35%); safety (SELECT only, limits, no personal data) (25%); transparency (SQL shown, uncertainty stated) (25%); cost per question (15%).

Project 5: Enterprise RAG knowledge assistant

  • Problem: staff cannot find policies, procedures and past decisions across many documents.
  • Requirements: chunking and indexing of at least 20 documents; retrieval with citations; "not found" when the answer is absent; access control so that restricted documents are never returned to unauthorised users; an evaluation of retrieval and answers.
  • Deliverables: the assistant, an evaluation report with retrieval hit rate and citation accuracy, and an access-control test.
  • Rubric: retrieval quality (30%); grounded answers with correct citations (30%); access control (20%); evaluation and monitoring (20%).

Project 6: AI agent for business operations

  • Problem: a support team wants an agent that triages tickets, looks up orders and drafts replies, with approval for anything that changes a record.
  • Requirements: read tools and at least one write tool behind approval; a step limit and budget; a regression suite of at least 30 tasks including forbidden actions; traces; cost per successful task.
  • Deliverables: the agent, the suite and its results, the trace of a sample run, and a release checklist.
  • Rubric: task completion on the suite (30%); safety tests passed (30%); traces and monitoring (20%); cost and latency (20%).

Project 7: MCP-powered business assistant

  • Problem: one assistant should answer questions using a CRM, a ticket system and a help centre, through a common protocol.
  • Requirements: an MCP server with read tools for two systems (you may use sample data), scoped permissions per tool, logging of every call, and an injection test.
  • Deliverables: the server, a tool list with roles and fields, the logs of a demo session, and the test results.
  • Rubric: tool design and scoping (30%); security tests (30%); logging and audit (20%); documentation for other developers (20%).

Project 8: Industry-specific capstone (choose one)

Choose an industry you know (retail, real estate, healthcare administration, logistics, education, finance operations) and combine any two earlier projects around one question in that industry. Write the problem with a named user, a decision, the data you would need and the data you can actually obtain, and deliver a working version with a clear limit statement.

  • Rubric: relevance to the industry and the user (35%); technical quality (35%); honesty about data and limits (30%).

Portfolio checklist (every project)

  • [ ] A README with the problem, the data source, how to run the project and the result.
  • [ ] Code and data in a repository, with no secrets or personal data.
  • [ ] Tests or checks, with the results shown.
  • [ ] One chart, table or screenshot on the first page of the README.
  • [ ] A clear limitations section, including what you would do next.
  • [ ] A 5-minute walkthrough (video or written) that an employer can follow.
  • [ ] The rubric, filled in honestly by you before you share the work.
Interview cornerWhat makes a portfolio project credible?

A specific problem, real or realistic data, a result that is checked against something, a clear statement of limits, and evidence that you tested it. Employers can tell a project that was finished from one that was only started; the checklist is how to finish it.

Career Readiness Check: Know Where You Stand Before You Apply

Use a structured self-check of eight readiness statements to see whether you are ready to apply for analyst roles, which topics to close first, and how to turn each gap into a short plan. Includes the scoring bands and a plan template.

● Gap-fill lesson✦ 2026Beginner⏱ 45 min

Why a readiness check

Many people apply for jobs before they can do the work they will be asked to do, or they keep studying long after they are ready. A readiness check replaces a feeling ("I think I'm ready") with evidence ("I can write a window function from memory and I have two published projects"). It is a planning tool, not a judgement of your potential.

The eight statements

Answer yes only if you could demonstrate the statement today, without notes, to someone who knows the subject.

# Statement Evidence that proves it
1 I can write SQL joins, window functions and cohort queries from memory. Write a cohort query on a sample database in 15 minutes
2 I can build a dashboard with a star schema and DAX measures. A published report with at least eight measures and a data model diagram
3 I can clean data and explain every step. A cleaning notebook or workbook, with the reasons for each change
4 I can explain a model's metrics to a non-technical person. A two-minute explanation of MAE and R-squared for a manager, recorded
5 I have two published projects with READMEs. Two links, each with a README that states the problem and the result
6 I can describe an ETL pipeline and its tests. A diagram of a pipeline with the checks at each step
7 I can explain RAG and a basic agent. A short explanation plus a working demo or a diagram of the loop
8 I can explain privacy basics for personal data. A one-page summary of how you would handle customer data in a project

Scoring

Yes answers What it means Next step
10 or more of the 16 extended items (see below) Ready to apply for analyst roles with a portfolio Apply, keep one project in progress, and prepare for interviews
7 to 9 Close to ready Complete the missing topics in the matching lesson and build one more project
Fewer than 7 Build the foundations first Return to the foundation topics in the roadmap and repeat the check in a month

The eight statements above are a core check. For the 16-item version, add eight items that match your target role: for example, "I can write an Airflow DAG" for a data engineer, or "I can run a churn model with a validation set" for a data scientist. Score out of 16 and use the same bands.

::::warn Be honest with yourself A "yes" that depends on a tutorial you followed last week is not a yes. Ask: could I do this again tomorrow, without the notes? If the answer is no, mark it "not yet" and make it a task. ::::

From gap to plan

For each statement you cannot yet say yes to, write one row of a plan:

Gap Action Time Evidence I will produce Review date
Window functions Complete the window-function exercises, then solve five new problems without notes 2 hours over two weeks Five solved problems with explanations Two weeks from today
Explaining metrics Record a two-minute explanation of MAE and R-squared 1 hour Recording reviewed by a peer One week from today

Keep the plan to three gaps at a time. Too many gaps at once means none is closed.

Reviewing progress

Repeat the check every four to six weeks. Expect the score to move up in steps, and expect a plateau when you are learning something hard. A plateau is not failure; it means you are working on the real difficulty. Share the result with a mentor or a study partner, and ask them to check one of your "yes" answers.

Applying when you score well

When you are ready:

  1. Choose three target roles and read five job descriptions for each. List the skills that repeat.
  2. Match your two best projects to those skills, and put the matching skill first in your CV.
  3. Prepare for the interview types in the earlier lessons: technical questions, scenarios and STAR answers.
  4. Apply to a manageable number of roles each week, and track each application with its date and status.

I am working on window functions in SQL, and I am practising explanations for non-technical managers." This is honest, specific, and shows a plan.

A Realistic 12-Month Roadmap for a Beginner

Plan a year of learning in twelve steps, from Excel and SQL foundations through business intelligence, Python, statistics and machine learning, data engineering and cloud, GenAI and agents, to a portfolio and interview preparation. Each stage has weekly hours, a milestone, an assessment, and a plain statement of what employers generally expect.

● Gap-fill lesson✦ 2026Beginner⏱ 90 min
By the end of this lesson you can
  • Plan twelve months of learning with weekly hours and milestones
  • Choose the order of topics and explain why it matters
  • Set an assessment for each stage that proves the skill
  • Set realistic expectations about what employers look for

Why a roadmap, and why realistic

A roadmap turns a vague wish ("I want to work with data") into a sequence of skills, each proven by a piece of work. The timing matters: a beginner who plans ten hours a week and finishes in twelve months has a real chance; a plan of thirty hours a week for three months usually stalls by the fourth week.

Case studyTwo learners, one year

Two learners start in January with the same goal. The first studies whenever motivated and skips the projects; by December she has watched many videos and has nothing to show. The second follows a roadmap of about ten hours a week, finishes a project each stage and keeps a record of each milestone. By December he has three published projects and a plan for interviews. The difference is the proof, not the hours.

The twelve months

Months Focus Hours per week Milestone Assessment
1–2 Foundation: Excel, SQL basics, basic statistics, business analytics basics About 10 A cleaned dataset with a five-measure summary A timed SQL test and an Excel cleaning exercise
3–4 Business intelligence: Power BI, star schema, DAX, dashboard design About 10 A published dashboard with row-level security Dashboard review against a rubric
5–6 Programming and data: Python, pandas, visualisation, Git and GitHub About 12 A Python exploratory analysis of a public dataset in GitHub Code review with tests
7–8 Machine learning and statistics: supervised learning, evaluation, a churn model About 12 A churn model with a business recommendation Model evaluation and explanation
9–10 Data engineering and cloud: warehouse concepts, ETL and ELT, dbt, Airflow, one cloud About 12 A three-layer pipeline with tests Pipeline review and a failure drill
11 GenAI, agents and MCP: LLM APIs, RAG, agents, MCP About 12 A RAG assistant with citations and an evaluation Evaluation report
12 Portfolio and interviews: two published projects, CV, LinkedIn, mock interviews, readiness check About 15 Three mock interviews and two published projects Interview rubric

The hours are a guide. A week with fewer hours is fine if the milestone is still reached; it is better to extend a stage than to skip its assessment.

Why this order

  • Excel and SQL first because every later skill reads and writes tables. A learner who cannot join two tables cannot build a dashboard, a model or a pipeline.
  • Business intelligence before programming because the first useful output, a dashboard, needs no code and proves the learner can answer business questions.
  • Python before machine learning because models are built with code, and the data preparation takes most of the effort.
  • Statistics before machine learning because the evaluation of a model is statistics; without it, a high accuracy number means little.
  • Data engineering after analytics because pipelines exist to feed the analysis; the learner understands what the pipeline must deliver before building it.
  • GenAI and agents near the end because they depend on the data, retrieval and evaluation skills earlier, and they are where mistakes are most expensive without those skills.

::::tip Protect the assessments An assessment is the proof that the stage is complete. A learner who skips it has consumed the content without the skill. Book the assessment in the calendar before starting each stage. ::::

What each milestone proves

Milestone Skill it proves
Cleaned dataset with five measures Cleaning, checking and summarising data
Published dashboard with RLS Modelling, measures, sharing and access control
Python analysis in GitHub Code, version control and reproducible analysis
Churn model with recommendation Modelling, evaluation and communicating a decision
Three-layer pipeline with tests Engineering reliability and data quality
RAG assistant with evaluation Retrieval, grounding and measuring AI quality
Two published projects and mock interviews Ability to show work and explain it under questioning

What employers generally expect

Employers look for working projects with code and data, clear documentation, measured results, the ability to explain trade-offs, and a steady record of learning. A roadmap cannot promise a job or a salary, and this one does not. It can make a candidate's evidence clear and specific.

Watch outExpect the first role to be a stepping stone

Entry-level roles in analytics and data are competitive, and job titles vary between employers. A first role that uses part of the skill set is a good result, and the portfolio is what moves the next step.

Adjusting the plan

  • If a stage's assessment is failed, repeat the stage's milestone before moving on.
  • If your time drops, extend each stage rather than dropping the portfolio work.
  • If you already know one stage, take its assessment early and move on.
  • Review the roadmap at the end of each stage: what took longer, what helped, and what to change.
Interview cornerHow would you explain your learning plan to an interviewer?

Name the stages in order and the milestone each produced: a dashboard, a model, a pipeline, a RAG assistant. Explain why the order matters, show the two published projects, and say what you would learn next. Interviewers listen for a clear plan with evidence, not a long list of courses.

::::key What to remember - A realistic roadmap has weekly hours, a milestone and an assessment for each stage. - The order follows dependencies: data first, then analysis, programming, models, pipelines and AI. - Each milestone proves a specific skill; the portfolio makes the proof visible. - Employers look for evidence, clear documentation and explained trade-offs. - Extend a stage rather than skipping its assessment. ::::
